# arch.py

## 1. что это за файл и за что он отвечает

arch.py это переводчик между моделью в формате hugging face и движком `tier.cpp`. движок сам не читает config.json и не знает имён тензоров разных семей. ему нужно короткое текстовое описание модели (файл `tier_arch.txt`), где уже всё разложено: сколько слоёв, какая ширина, какие нормы есть, как называется каждый тензор слоя, какой rope у каждого слоя. arch.py это описание и делает.

главная мысль файла: модель описывается по общим признакам, а не по списку известных моделей. всё что можно, берётся из самих тензоров (их имена и формы в заголовке safetensors), а config.json нужен только для того, чего в тензорах нет: тип внимания по слоям, rope, активация, eps, softcap, множители.

кроме описания, файл умеет склеить веса из нескольких частей в один `model.safetensors` и перевести f16 и f32 в bf16 (команда `merge`), потому что движок читает только один файл bf16.

кто его вызывает:

1. `tierlm.py`: функция `model_info()` через `amod()` импортирует модуль, зовёт `arch.tensors()`, `arch.describe()`, `arch.summary()` и `arch.write()`. описание пишется в каталог данных программы `DATA/arch/<хэш>.txt`, а путь к нему уходит движку в переменной `TIER_MODEL_DESC`. папка модели при этом только читается. ещё `tierlm.py` запускает `arch.py merge <папка>` как отдельный процесс (действие "склеить").
2. `hub.py`: зовёт `arch.describe(td, (T, files))` с тензорами, которые прочитаны по сети из заголовков на hugging face, то есть модель описывается до загрузки весов. ещё берёт `arch.load_json`, `arch.text_cfg`, `arch.summary`.
3. `fetch_model.sh`: после загрузки модели зовёт `describe`, если все причины отказа это только "нужно объединение", то зовёт `merge` и ещё раз `describe`, потом печатает `summary`.
4. `auto.sh`: если в файле описания нет строки `layers`, берёт число слоёв из вывода `arch.py desc <папка>`.
5. `tier.cpp` сам arch.py не вызывает, он читает готовый файл (функция `arch_load`, файл берётся из `TIER_MODEL_DESC`, иначе `tier_arch.txt` рядом с файлом весов). в сообщении об ошибке движок советует запустить `python3 arch.py <папка модели>`.

что вызывает сам arch.py: других файлов проекта не импортирует. из внешнего нужен только numpy и только для `merge` (импорт внутри функции).

## 2. как он работает

### команды

```
python3 arch.py <папка модели>
python3 arch.py info <папка> [--json]
python3 arch.py desc <папка>
python3 arch.py merge <папка> [--keep]
python3 arch.py g4check <папка>
```

| команда | что делает | код выхода |
|---|---|---|
| `<папка>` | описывает модель, если описание получилось, пишет `<папка>/tier_arch.txt`, печатает сводку | 0 если поддерживается полностью, 2 если есть хоть одна причина отказа |
| `info <папка>` | только сводка одной строкой (функция `summary`) | 0 или 2, как выше |
| `info <папка> --json` | словарь описания без `freqs` и `files`, плюс поля `why` (список причин), `ok` (нет причин), `merge` (все причины это только объединение) | 0 или 2 |
| `desc <папка>` | текст описания в stdout, файл не пишется | 0 если описание есть, 2 и строка `unsupported ...` если описание не получилось совсем |
| `merge <папка>` | склейка частей и перевод в bf16, ключ `--keep` оставляет исходные части | 0, при ошибке выход через `SystemExit` с текстом |
| `g4check <папка>` | сверка описания gemma 4 12b с эталонными числами, которые движок для неё ожидает | 0 если совпало, 1 если есть расхождения |

без аргументов печатается начало файла до первого `import` (там шапка с подсказкой) и выход с кодом 1.

переменных окружения arch.py не читает.

### что читается

1. `config.json` модели (если нет, пустой словарь).
2. `generation_config.json` (только ради `eos_token_id`).
3. заголовки safetensors: либо один `model.safetensors`, либо все части по `model.safetensors.index.json` (ключ `weight_map`). читаются только заголовки: 8 байт длины (little endian, `<Q`), потом json. ключ `__metadata__` выбрасывается. результат: словарь `{имя: (dtype, shape)}` и список файлов. подробности в метке г1.

### главный поток (`describe`)

1. config.json сливается в один плоский словарь функцией `text_cfg`: сначала значения по умолчанию из таблицы `CFG_DEFAULTS` для `model_type`, потом верхний уровень config.json, потом вложенный `text_config` (у моделей со зрением текстовая часть лежит там). таблица нужна потому, что transformers не пишет в config.json значения, которые совпадают со значениями класса по умолчанию, а у вложенного `text_config` так пропадает почти всё. без таблицы gemma 3 со зрением получила бы rope 10000 вместо 1e6 у полных слоёв. значения в таблице это значения классов transformers со старыми именами ключей, так их пишут файлы на hugging face (метка г2).
2. ищется контейнер слоёв (`layer_prefix`, метка к1): по всем тензорам, кроме побочных (`SIDE`: `vision`, `visual`, `audio`, `encoder`, `mm_proj`, `multi_modal`, `speech`, `image`, `mtp`), ищется кусок вида `...layers.N.`, `...h.N.`, `...blocks.N.`, `...layer.N.`. выигрывает префикс, у которого больше всего разных номеров. при равенстве выигрывает тот, где есть `language_model`, потом более короткий. число слоёв `nl` это максимальный номер плюс 1.
3. общий префикс текстовой части `pre` это `layer_prefix` без последнего звена. например для `model.language_model.layers.` это `model.language_model.`, для `layers.` пустая строка. эмбеддинги и финальная норма ищутся только под этим префиксом.
4. роли тензоров слоя 0 (`roles_of`, метка и1). потом идут жёсткие отказы, при них `describe` возвращает `(None, [причина])`:
   1. moe: в именах есть `experts` или в конфиге есть `num_experts`, `num_local_experts`, `n_routed_experts`, `enable_moe_block`.
   2. нет ни `q`, ни слитого `qkv` (линейное внимание, ssm).
   3. в слое 0 нет нужных ролей (`q`, `k`, `o` или `qkv`, `o`). в причину пишется, каких ролей нет, и первые 8 имён тензоров слоя 0, чтобы было видно, что там есть.
   4. какой то слой устроен иначе, чем слой 0 (смешанные блоки).
   5. нет матрицы эмбеддингов.
5. дальше собираются мягкие причины в список `why`. описание всё равно строится, но модель считается не поддерживаемой, и в файл они попадают строками `unsupported`. список причин:
   1. нет финальной нормы.
   2. слитые q, k, v с перемешанными по головам строками (`query_key_value`, `wqkv`), или строки `qkv_proj` не раскладываются на головы.
   3. mlp без затвора (только `fc1`, активация, `fc2`) или нет матриц mlp, нет `down`.
   4. разная ширина mlp по слоям.
   5. layernorm со сдвигом: у норм есть `bias`, или `norm_type` или `normalization` равно layernorm, или есть `layer_norm_eps` без `rms_norm_eps` (кроме exaone, у неё имя ключа такое, а норма rms). движок считает только rmsnorm.
   6. веса не bf16 (есть f16, f32, f64) или веса в нескольких файлах. текст этих причин содержит слово `merge`, по нему вызывающий код понимает, что модель починится склейкой.
   7. общий kv между слоями (`num_kv_shared_layers`), входы по слоям (`hidden_size_per_layer_input` плюс тензоры `per_layer`), двойной mlp (`use_double_wide_mlp`), двустороннее внимание (`use_bidirectional_attention` равно `True`, `all` или `text`, значение `vision` у gemma 4 касается только картинок и не мешает), параллельные ветки внимания и mlp.
   8. неизвестная активация, неизвестный вид rope, формы q и k не делятся на головы, разный множитель rope по слоям.
6. считаются общие числа и флаги (подробно в разделе 3), потом цикл по слоям строит список `L` с параметрами каждого слоя и таблицу частот `freqs` для слоёв, где обычной формулы движка не хватает.
7. возвращается словарь `A` и список `why`.

### формат `tier_arch.txt`

текст, одна запись на строку, ключ и значения через пробел. первая строка комментарий с `#`. функция `text(A, why)` пишет строки в таком порядке:

1. обязательные ключи: `family prefix layer_prefix hidden inter heads vocab eps softcap emb_scale attn_scale norm1p post_attn post_ffn qk_norm v_norm layer_scalar qkv_bias act tied`.
2. `head <имя>` только если выходная матрица отдельная.
3. необязательные ключи, только если значение не обычное: `rope_pairs rot`, `rope_mscale`, `qk_norm_full 1`, `resid_mul`, `logit_div`, `attn_softcap`.
4. `requires <список>`: перечень тех необязательных ключей из пункта 3, которые есть в файле. без них счёт неверен, поэтому движок, который какой то ключ не знает, должен отказать, а не пропустить его молча (метка н2). в `tier.cpp` при неизвестном слове в `requires` движок падает с просьбой пересобрать его.
5. `eos <id> <id> ...`.
6. `name <слот> <имя тензора>` для каждого слота. слоты: `iln q k v o gate up down paln pfln pofln qn kn ls qb kb vb final embed`. `-` значит "нет такого тензора". имена слоёв даны без префикса слоя (движок сам ставит `layer_prefix` и номер), `final` и `embed` без `prefix`, `head` полное имя.
7. `layers <число>`. эта строка должна стоять выше строк `layer`, движок по ней выделяет место.
8. `layer <i> <full> <hd> <nkv> <has_v> <window> <theta> <rot>` для каждого слоя: 1 если полное внимание, размер головы, число kv голов, есть ли своя v (0 значит v берётся из k), окно скользящего внимания (0 у полных), theta rope, сколько измерений головы вращается.
9. `freq <i> <числа>`: таблица обратных частот на `rot/2` пар, только для слоёв, где нужна.
10. `unsupported <причина>` для каждой мягкой причины. движок, увидев такую строку, печатает её и выходит.

окно внутри тензора пишется как `имя[начало:конец]` по строкам. так задаются слитые матрицы: q, k, v из `qkv_proj` и gate, up из `gate_up_proj`. движок (`arch_check_tensors` в `tier.cpp`) считает размер строки как число столбцов умножить на 2 байта, то есть окна работают только на bf16.

числа с плавающей точкой пишутся форматом `.9g`.

## 3. главные функции и разделы

### `load_json`, `st_header`, `tensors`

`load_json(p, d)` читает json, при любой ошибке чтения или разбора возвращает `d`. `st_header(path)` читает заголовок safetensors и возвращает `(заголовок, смещение начала данных)`, смещение это `8 + длина`. `tensors(mdir)` описано выше (метка г1). если нет ни одного файла, ни индекса, выход через `SystemExit`.

### `CFG_DEFAULTS`, `text_cfg`

таблица значений по умолчанию для семей `gemma3_text`, `gemma4_text`, `gemma2`, `gemma`, `llama`, `qwen2`, `qwen3`, `mistral`, плюс `gemma3` и `gemma4` как синонимы текстовых. порядок слияния важен: умолчание, потом верх конфига, потом `text_config`. метка г2.

### `rope_for(cfg, ltype)`

возвращает для типа слоя (`full_attention` или `sliding_attention`) три вещи: theta, словарь растяжения, долю поворота (метка е1).

1. `rope_parameters` бывает двух видов: словарь по типам слоёв (`{"full_attention": {...}, "sliding_attention": {...}}`) или один плоский словарь с `rope_theta` или `rope_type`. берётся нужный.
2. theta: из `rope_parameters`, иначе у скользящих слоёв `rope_local_base_freq` (если задано), иначе `rope_theta`, по умолчанию 10000.
3. растяжение: `rope_parameters`, иначе `rope_scaling`. у gemma 3 растяжение только у полных слоёв, поэтому для скользящих без `rope_parameters` оно обнуляется (метка е2).
4. доля поворота `partial_rotary_factor`, по умолчанию 1.0.

### `inv_freq(theta, sc, hd, rot, den, cfg)`

считает обратные частоты для пар `(i, i+half)`, где `i < rot/2`, и множитель для cos и sin (метка ж1). возвращает `(частоты или None, множитель, текст ошибки или None)`. `None` вместо частот значит, что хватает обычной формулы движка `theta^(-2i/hd)`.

`den` это знаменатель в показателе. у gemma 4 с частичным "пропорциональным" rope это `hd` (пары по всей голове), у остальных моделей с частичным rope это `rot`. базовые частоты `base[i] = theta^(-2i/den)`.

| вид (`rope_type` или `type`) | что делает |
|---|---|
| `default`, `proportional`, `dynamic`, нет | частоты не меняются. таблица отдаётся только если `den` не равно `hd`, иначе `None`. dynamic ntk меняет частоты только за пределом длины обучения, а мы туда не выходим (метка ж2) |
| `linear` | каждая частота делится на `factor` |
| `llama3` | длина волны `w = 2*pi/f`. если `w` меньше `om/high_freq_factor`, частота остаётся, если больше `om/low_freq_factor`, делится на `factor`, между ними плавный переход `s = (om/w - lo)/(hi - lo)`, частота `(1-s)*f/factor + s*f`. по умолчанию `lo=1`, `hi=4` |
| `longrope`, `su` | обучение и разговор идут в пределах исходной длины, поэтому берутся "короткие" множители `short_factor`, частота `f/short_factor[i]`. длина `short_factor` обязана быть `rot/2`, иначе ошибка. множитель cos и sin это `attention_factor` или `sqrt(1 + ln(fct)/ln(om))`, где `fct = max_position_embeddings / original_max_position_embeddings` (метка ж3) |
| `yarn` | границы `lo` и `hi` по `beta_fast` (32) и `beta_slow` (1) через `dim_of(nr) = den*ln(om/(nr*2*pi)) / (2*ln(theta))`. для каждой пары `ramp` от 0 до 1, доля без растяжения `ext = 1 - ramp` (метка ж4), частота `f/factor*(1-ext) + f*ext`. множитель `attention_factor` или `0.1*ln(factor) + 1` |
| другое | ошибка "rope пока не поддерживается" |

### роли тензоров: `ROLES`, `EMBED`, `FINAL`, `HEAD`, `SIDE`, `roles_of`

роль тензора определяется по двум общим признакам, которые есть у любого трансформера: имя ветки (внимание или mlp) и имя матрицы внутри неё (метка ж5). ветка внимания это `self_attn`, `self_attention`, `attention`, `attn`, `attn.attention`, `mixer`. ветка mlp это `mlp`, `feed_forward`, `ffn`, `block_sparse_moe`. так узнаются и llama подобные с другими именами (exaone: `attn.attention.q_proj`, `mlp.c_fc_0`, internlm: `attention.wq`, `feed_forward.w1`), и gemma, и qwen.

| роль | что это |
|---|---|
| `q k v o` | проекции внимания |
| `qkv` | слитые q, k, v |
| `gate up down` | mlp с затвором |
| `gate_up` | слитые gate и up (сначала gate, потом up, метка л3) |
| `fc1` | mlp без затвора, нужен только чтобы дать понятную причину отказа |
| `iln` | норма перед вниманием |
| `pal` | `post_attention_layernorm` и синонимы. у llama это норма перед mlp, у gemma 2 и дальше и у olmo 2 это норма после внимания (метка ж6) |
| `psal` | норма выхода внимания, когда перед mlp есть отдельная норма (glm 4, метка ж7) |
| `pfln` | норма перед mlp (`pre_feedforward_layernorm`) |
| `pofln` | норма после mlp |
| `qn kn` | нормы q и k |
| `ls` | `layer_scalar`, множитель слоя |

`roles_of(T, lp, l)` для слоя `l` берёт суффиксы имён после `<layer_prefix><l>.`, для каждой роли ищет суффикс по шаблону `^шаблон(\.weight)?$`, при нескольких совпадениях берёт первый по сортировке. смещения ищутся отдельно и кладутся как `<роль>_bias`. результат `{роль: суффикс}`.

`cfg_get(cfg, *keys, d)` возвращает первое заданное значение из синонимов ключа конфига, потому что у разных семей одно и то же называется по разному (метка з1).

### `layer_prefix(T)`

описано в главном потоке, метка к1.

### `describe(mdir, tens=None)`

главная функция, поток описан выше (метка л1). `tens` можно передать готовым `({имя: (dtype, shape)}, [файлы])`, так `hub.py` описывает модель по заголовкам с сайта без загрузки.

подробности по частям:

1. слитые матрицы (метка л2). если строки ролей идут подряд (q, потом k, потом v, или gate, потом up), движок читает окно внутри тензора. так можно только для `qkv_proj` и `Wqkv`. размер головы `hd0` из `head_dim` или `hidden/heads`, число kv голов `nkv0 = (rows/hd0 - heads)/2`, проверка `(heads + 2*nkv0)*hd0 == rows`. если сошлось, `qkv_split = (heads*hd0, nkv0*hd0)`.
2. ширина mlp `inter`: строки `gate` или половина строк `gate_up`. у всех слоёв должна быть одна.
3. схема норм блока (метки л4, л5, л6, л7). в описании четыре слота: `iln` (перед вниманием), `paln` (после внимания, до сложения с остатком), `pfln` (перед mlp), `pofln` (после mlp). раскладка такая:
   1. если есть `pfln`, это "бутерброд" gemma 2 и дальше, нормы до и после каждой ветки: `pfln` идёт в слот перед mlp, `pal` (или `psal`) в слот после внимания.
   2. если нет `iln`, но есть `pal` и `pofln`, это olmo 2, нормы только после ветки: перед mlp ничего, `pal` в слот после внимания.
   3. иначе это llama: `pal` это норма перед mlp и идёт в слот `pfln`, а слот после внимания берёт `psal`, если она есть.
   важно: у llama тензор `post_attention_layernorm` попадает в слот `pfln`, а не в `paln`. название тензора в hugging face обманчиво, слот определяется схемой.
4. флаги семьи: `gemma` если `model_type` начинается с gemma, `g4` если с gemma4. `qk_norm` если есть роль `qn`, `qkv_bias` если есть смещение у q, `layer_scalar` если есть `ls`.
5. множители granite (метки л9, л10): `embedding_multiplier` и `attention_multiplier` ложатся в уже существующие масштабы эмбеддингов и внимания. `residual_multiplier` (выход ветки умножается на него перед сложением с остатком) и `logits_scaling` (логиты делятся на него) отдельных мест не имеют и пишутся ключами `resid_mul` и `logit_div`.
6. типы слоёв: если в конфиге есть `layer_types` нужной длины, берутся они. иначе:
   1. gemma 4: полный слой, если у него нет своей `v` или номер `(l+1)` делится на 6.
   2. gemma 3: полный каждый `sliding_window_pattern` слой (по умолчанию 6).
   3. gemma 2: чётные скользящие, нечётные полные.
   4. есть `sliding_window` и (`use_sliding_window` или mistral): все скользящие.
   5. иначе все полные.
7. активация: всё, где есть `gelu`, считается как `gelu_tanh`, `silu`, `swish`, `swiglu` как `silu`, остальное причина отказа.
8. `no_rope_layers` (smollm3, метка л11): список длины `nl`, 1 значит слой с rope, 0 значит без позиционного кодирования (`rot = 0`).
9. цикл по слоям:
   1. если в слое нет `q` и нет разрезаемого `qkv`, цикл обрывается, причина уже записана (метка л12).
   2. строки q и k: `qr`, `kr`.
   3. размер головы сначала из весов: если есть норма q и её длина не равна всей проекции, это норма по голове и её длина и есть `hd`. веса точнее конфига, у gemma 4 головы полных и скользящих слоёв разные (метка л13). иначе `head_dim` из конфига, иначе `qr/heads`.
   4. если длина нормы q равна всей проекции q, это норма по всей проекции, а не по голове (olmo 2), ставится `qk_norm_full` (метка л14).
   5. если `heads` не было в конфиге, оно выводится как `qr/hd`. проверка `qr == heads*hd` и `kr` делится на `hd`.
   6. rope слоя через `rope_for`. у gemma 4 на полных слоях без `rope_parameters` доля 0.25 и theta 1e6 (если в конфиге стоит умолчание 10000).
   7. `rot = round(hd*frac)`, округлённое вниз до чётного.
   8. частичный rope (метка л15): у gemma 4 пары идут по всей голове `(i, i+hd/2)`, у остальных внутри вращаемой части `(i, i+rot/2)`. во втором случае `rope_pairs` становится `rot`, а знаменатель частот `rot`.
   9. `inv_freq`, если вернулась таблица, она идёт в `freqs[l]`. множитель cos и sin собирается в множество, у всех слоёв он должен быть один.
   10. в `L` кладётся `dict(full, hd, nkv = kr/hd, has_v, window, theta, rot)`. `has_v` равно 1, если у слоя есть своя `v` или q, k, v слиты.
10. масштаб внимания `attn_scale`: у gemma 4 1.0, у остальных gemma `query_pre_attn_scalar^-0.5` (или `hd^-0.5`), если задан `attention_multiplier`, то он, иначе `hd^-0.5` первого слоя.
11. `eos`: все целые из `eos_token_id` в `generation_config.json`, в слитом конфиге и в исходном конфиге, без повторов. у gemma 4 добавляется 106 (конец реплики).
12. имена: `W()` добавляет `.weight`, если его нет. окна для `qkv` и `gate_up` пишутся как `имя.weight[a:b]`.
13. масштаб эмбеддингов `emb_scale`: у gemma `sqrt` (умножение на корень из ширины), иначе `embedding_multiplier` или 1.
14. `norm1p` равно 1 у gemma кроме gemma 4: вес нормы хранится как `w - 1`, движок умножает на `(1 + w)`.
15. `v_norm` равно 1 у gemma 4.
16. `tied` равно 1, если отдельной выходной матрицы (`lm_head`, `output`, `embed_out`) нет, тогда выход считается через эмбеддинги.
17. `softcap` из `final_logit_softcapping`, `attn_softcap` из `attn_logit_softcapping` (gemma 2: оценки внимания `c*tanh(s/c)`, метка н1).
18. `params` это сумма элементов всех тензоров файла, включая побочные части.

### `text(A, why)`, `write(A, why, path)`, `summary(A, why)`

`text` собирает описание в формате выше, `write` пишет его в файл как есть. `summary` даёт одну строку по русски для человека: семья, число параметров в миллиардах, слоёв (из них полного внимания), ширина, mlp, головы q и kv, словарь, активация, особенности, и в конце причины отказа, если они есть.

### `merge(mdir, keep=False)`

склейка частей в один `model.safetensors` и перевод f16 и f32 в bf16 (метка п1).

1. список частей из `model.safetensors.index.json`, если его нет, то один `model.safetensors`.
2. если переводить нечего и файл один, печатается сообщение и выход.
3. новый заголовок: тензоры по алфавиту, данные подряд без дыр, f16 и f32 становятся `BF16` с размером `элементов*2`, остальные типы копируются как есть. json пишется компактно и дополняется пробелами до кратности 8 байт.
4. проверка места: нужно размер нового файла плюс 1 гиб свободного места в папке модели, иначе отказ.
5. запись в `model.safetensors.part` кусками по 64 миб (кратно размеру элемента). перевод в bf16 с округлением к ближайшему чётному, как в движке (метка п2): `(u + 0x7FFF + ((u >> 16) & 1)) >> 16` над битами f32. у f16 при этом теряются 3 младших бита мантиссы (10 бит у f16 против 7 у bf16), об этом пишется в итоговом сообщении. для каждого тензора считается crc32 записанных байт.
6. сверка (метка п3): записанный файл перечитывается с диска, crc32 каждого тензора сравнивается. при расхождении `.part` удаляется, исходные файлы не трогаются.
7. только после успешной сверки `.part` переименовывается в `model.safetensors` (`os.replace`, атомарно), и если не задан `keep`, удаляются части и индекс.

### `g4check(mdir)`

сверка описания gemma 4 12b с эталонными числами, которые движок для этой модели ожидает (метка р1). нужна, чтобы проверить, что общий разбор по признакам даёт для этой модели тот же счёт. эталон: `hidden 3840`, `inter 15360`, `heads 16`, `vocab 262144`, `layers 48`, `eps 1e-6`, `softcap 30`, `emb_scale sqrt`, `attn_scale 1`, `norm1p 0`, `post_attn 1`, `post_ffn 1`, `qk_norm 1`, `v_norm 1`, `layer_scalar 1`, `qkv_bias 0`, `act gelu_tanh`, `tied 1`. по слоям каждый шестой полный с `hd 512`, `nkv 1`, без своей v, `theta 1e6`, `rot 128`, остальные скользящие с `hd 256`, `nkv 8`, `window 1024`, `theta 1e4`, `rot 256`. таблиц частот быть не должно, `eos` ровно 1 и 106. возвращает список расхождений, пустой список значит совпало.

### `__main__`

разбор команд из таблицы раздела 2. `desc` печатает описание в stdout, так его можно взять без записи файла (метка р2).

## 4. что важно знать, когда правишь

1. формат `tier_arch.txt` это договор с `tier.cpp` (`arch_load`). если добавляешь ключ, его надо научить читать в движке. если без нового ключа счёт неверен, его обязательно надо вписать в `requires` (список в `text()` и множество `KN` в движке), иначе старый движок посчитает модель неправильно и не скажет.
2. движок требует все ключи из своего списка `NEED_KEYS` и все слоты из `NEED_SLOTS`. слот без тензора пишется как `-`, но строка `name` должна быть.
3. строка `layers` должна стоять выше строк `layer`.
4. окна `[a:b]` движок режет по строкам и считает 2 байта на элемент, поэтому окна валидны только для bf16 весов. это одна из причин, почему веса всегда приводятся к одному файлу bf16.
5. тексты причин про объединение должны содержать слово `merge`. по нему `tierlm.py`, `hub.py`, `fetch_model.sh` и `info --json` решают, что модель можно починить склейкой. если поменять текст, они перестанут это понимать.
6. жёсткий отказ (`A` равно `None`) и мягкий (`why` не пуст) это разные вещи. при мягком описание всё равно пишется (с `unsupported`), сводка печатается, код выхода 2. движок на строке `unsupported` выходит.
7. роли ищутся по регуляркам, первое совпадение по сортировке побеждает. если добавляешь синоним, проверь, что он не совпадает с чужой ролью (например короткие `q`, `k`, `v`, `o` стоят последними в альтернативе, но регулярка якорная, поэтому `q` не поймает `q_proj`).
8. `roles_of` пересчитывается при каждом вызове `has()` и `tn()`, кэша нет. на моделях с тысячами тензоров это заметно по времени, но не по смыслу.
9. размер головы берётся сначала из нормы q, потом из конфига. если у модели норма q по всей проекции, это отдельный случай `qk_norm_full`, его надо не перепутать с нормой по голове.
10. `CFG_DEFAULTS` должна совпадать со значениями классов transformers. если значение там неверное, модели, у которых ключа нет в config.json, получат неверный rope или eps без всякой ошибки.
11. все виды gelu считаются как gelu с tanh. точный gelu через erf отдельно не различается.
12. квантованные типы весов (i8, u8, f8 и подобные) arch.py сам не отсекает, это делает `tierlm.py` (множество `QDT`). в `merge` переводятся только f16 и f32, f64 копируется как есть и после склейки причина про тип останется.
13. перевод в bf16 не обрабатывает nan и inf отдельно, веса предполагаются конечными.
14. `merge` удаляет исходные части только после сверки по crc32 с перечитанным с диска файлом. этот порядок нельзя ломать: сначала `.part`, сверка, `os.replace`, и только потом удаление.
15. описание по заголовкам с сайта (через `hub.py`) и по локальным файлам должно давать одно и то же, поэтому `describe` не должна читать ничего, кроме конфигов и словаря тензоров.
