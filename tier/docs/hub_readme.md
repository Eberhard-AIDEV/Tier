# hub.py

метки вида а1, и3, аб4 в этом описании совпадают с метками в коде hub.py. по метке в файле комментариев с тем же именем лежит пояснение к этому месту кода.

## 1. что это за файл и за что он отвечает

hub.py это каталог моделей hugging face для программы. он делает три вещи (метка а1):

1. живой список текстовых моделей с сайта: поиск, порядок, фильтр по размеру и по автору, кэш на диске и работа без сети.
2. сведения об одной модели по имени или ссылке до загрузки весов: данные репозитория из api, `config.json` и заголовки safetensors (несколько киб, запрос с заголовком `Range`). по ним `arch.py` решает, поддерживает ли модель движок.
3. прогноз: поместится ли модель на диск, в озу и в видеопамять этой машины, сколько займёт шаг обучения и с какой скоростью пойдёт разговор.

весь файл работает без загрузки весов: из сети берутся только описания и первые байты файлов. поэтому решение "годится модель или нет" и прогноз видны в окне сразу, до того как человек решит что то качать.

кто его вызывает:

1. `tierlm.py` через `hmod()`: `hub_catalog()` зовёт `catalog()`, `hub_mark()` зовёт `mark()`, `hub_check()` зовёт `check()`, `hub_info()` зовёт `info()`, `forecast()` и `known()`, `hub_get()` зовёт `repo_of()`. окно (`ui.py`, `ui.qml`) ходит в hub.py только через эти функции `tierlm.py`.
2. командная строка: `hub.py info` и `hub.py list`.

что вызывает сам:

1. `arch.py`: `arch.describe(td, (T, files))` с тензорами из заголовков, полученных по сети, `arch.load_json`, `arch.text_cfg`, `arch.summary`.
2. `tmpl.py`: `tmpl.manual(family)`, чтобы понять, можно ли обойтись без шаблона диалога.
3. `hwprobe.py` (метка а2): замеры машины для прогноза. шина карты (`hwprobe.pcie`), резерв озу (`hwprobe.ram_reserve_now`), скорость чтения диска (`hwprobe.disk_read_bps`), оценка видеопамяти под активации (`hwprobe.pack_fit`, `hwprobe.act_bytes`, `hwprobe.TRAIN_ACT_SHARE`, `hwprobe.PACK_LO`). импорт необязательный: если `hwprobe` не загрузился, прогноз считается по запасным правилам, описанным ниже.
4. файл `hub_known.json` рядом с программой (пометки проверки).

## 2. как он работает

### командная строка

```
python3 hub.py info <имя или ссылка> [--fresh]
python3 hub.py list [--search текст] [--sort downloads|likes|trending|modified|created] [--limit N] [--org автор]
                    [--min-b млрд] [--max-b млрд] [--task tag] [--supported] [--no-check] [--fresh] [--offline]
```

`info` печатает json со сведениями о модели. кэш действует сутки, `--fresh` его не смотрит. ключ hugging face берётся из `HF_TOKEN`.

ключи `list`:

| ключ | смысл | по умолчанию |
|---|---|---|
| `--search` | часть названия. вид `автор/часть` задаёт ещё и автора | пусто |
| `--sort` | `downloads`, `likes`, `trending`, `modified`, `created` | `downloads` |
| `--limit` | сколько строк выдать | 30 |
| `--org` | только этот автор (организация) | пусто |
| `--min-b`, `--max-b` | границы размера в миллиардах параметров, 0 значит без границы | 0 |
| `--task` | значение `pipeline_tag` на сайте, можно несколько раз | `text-generation`, `image-text-to-text`, `any-to-any` |
| `--supported` | только модели, которые поддерживает движок. список расширяется, пока не наберётся `--limit` | выкл |
| `--no-check` | не проверять поддержку по заголовкам, брать только кэш | выкл |
| `--fresh` | не смотреть кэш списка | выкл |
| `--offline` | без сети, только кэш и сохранённые сведения | выкл |

`list` пишет json список в stdout, а в stderr одну строку: откуда список, сколько строк, сколько из них проверено и есть ли продолжение (метка ч1). в строках остаются поля `repo`, `проверка`, `заметка`, `поддержка`, `почему`, `склейка`, `загрузок`, `нравится`, `изменена`, `закрыта`, `всего_параметров`, `задача`, `тип_модели`, `байт_весов`, `проверка_ошибка`.

без аргументов или с неизвестной командой печатается начало файла до первой строки `import` и программа выходит с кодом 1.

### переменные окружения

| переменная | смысл | по умолчанию |
|---|---|---|
| `HF_ENDPOINT` | адрес сайта (зеркало). читается один раз при импорте модуля в константу `HF` | `https://huggingface.co` |
| `HF_TOKEN` | ключ hugging face, только в режиме командной строки. из `tierlm.py` ключ приходит аргументом `token` | нет |
| `TIER_DATA` | каталог данных программы, кэш лежит в `<TIER_DATA>/hub` | см. ниже |
| `XDG_DATA_HOME` | если нет `TIER_DATA`, кэш лежит в `<XDG_DATA_HOME>/tierlm/hub` | `~/.local/share` |
| `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY`, `http_proxy` | прокси для urllib. если адрес прокси начинается с `https://`, при сбое соединения запрос повторяется напрямую | нет |

переменные, которые читает `hwprobe.py` (например потолок памяти из `tier.conf` и `TIER_RAM_OTHER_GIB`), влияют на прогноз через `reserve()`, сам hub.py их не читает.

### файлы

1. `hub_known.json` рядом с программой (метка а3): пометки проверки. формат `{"статусы": {"org/name": {"проверка": "...", "заметка": "..."}}}`. значения поля `проверка`: "карта" (проверено на видеокарте целиком, обучение и разговор), "формулы" (прямой проход совпал с эталоном на процессоре, на карте ещё не проверено), всё остальное "нет". пока файла нет, берутся запасные пометки из `SEED` (метка а4).
2. кэш одной модели: `<кэш>/<org>__<name>.json`, словарь `info()` с полем `когда` (время unix).
3. кэш списка: `<кэш>/catalog_<20 знаков sha1>.json`, где sha1 берётся от `[search, sort, limit, org, min_b, max_b, tasks, HF]`. содержимое `{"когда", "rows", "ещё"}`.

запись всегда идёт через временный файл `<файл>.<pid>.<поток>.part` и `os.replace` (функция `_save`, метка л1). проверка идёт в несколько потоков, и общий для всех временный файл они затирали бы друг у друга. при ошибке записи временный файл удаляется, а исключение наружу не выходит.

### константы

| имя | что | метка |
|---|---|---|
| `SORTS` | имя порядка для командной строки и окна и соответствующее поле `sort` в api | а5 |
| `TTL` | сколько живёт кэш списка: сутки для `downloads`, `likes`, `created`, час для `trending` и `modified` (список "в тренде" быстро устаревает) | а6 |
| `TASKS` | какие `pipeline_tag` считать текстовыми моделями | а7 |
| `EXPAND` | какие поля просить у api в списке | |
| `KEEP` | какие файлы репозитория нужны движку, кроме весов | |
| `HEAD1` | сколько первых байт файла просить сразу (128 киб) | а8 |
| `HF` | адрес сайта без косой черты в конце | |
| `NETERR` | набор исключений, которые значат "сеть или ответ, который не разобрать" | а9 |
| `SHOW` | какие поля сведений `mark()` переносит из кэша в строку списка | |
| `SORTKEY` | по какому полю строки сортировать для каждого порядка | |

почему три `pipeline_tag` (метка а7): одного `text-generation` мало. модели вроде gemma 3 и 4 и qwen vl с рабочей текстовой частью на сайте помечены как `image-text-to-text` или `any-to-any`, и фильтр по одному `text-generation` выкинул бы основную модель программы. годна ли текстовая часть, решает `arch.py`. у репозитория один `pipeline_tag`, поэтому списки по разным тегам не пересекаются и от повторов отдельно не чистятся.

### сведения о модели (`info`)

`info(repo_or_url, token, fresh, max_age=86400, max_shards=0)` (метка и1). исключения наружу не выходят, ошибки кладутся в поле `ошибка`.

1. `repo_of()` приводит строку к виду `org/name` (метка б1). понимает просто имя, ссылку на страницу (`huggingface.co/...`, `hf.co/...`, с `www.`, с `models/` и без) и ссылку на файл (всё после имени отрезается). если не вышло, ошибка "не является именем модели".
2. если кэш моложе `max_age`, в нём нет ошибки и не задан `fresh`, возвращается кэш.
3. запрос `GET <HF>/api/models/<repo>` с параметром `blobs=true`. ошибка сети превращается в понятный текст функцией `_why_http()`: 401 и 403 значат закрытую модель (нужно согласие на странице модели и ключ), 404 значит, что такой модели нет, другой код и отсутствие связи описываются отдельно.
4. из `siblings` берутся имена и размеры файлов (размер из `size` или из `lfs.size`), фильтр `wanted()` (метка в1): только файлы в корне репозитория, из списка `KEEP` (конфиги, токенизатор, шаблоны, индекс весов) и все `.safetensors`, кроме `consolidated*` (это копия весов в формате mistral, движку она не нужна).
5. если весов safetensors в корне нет, `поддержка` ставится `False` с причиной. если в репозитории есть gguf, к причине добавляется, что его можно взять как квантованную базу. результат сохраняется в кэш.
6. если `max_shards` больше нуля и частей весов больше, возвращается ошибка "проверка выполняется при открытии модели". так массовая проверка списка не делает сотни запросов для моделей с большим числом частей, а сама модель проверится, когда её откроют.
7. во временную папку качаются `config.json`, `generation_config.json`, `tokenizer_config.json`, если они есть в репозитории. без `config.json` дальше нельзя, сбой остальных файлов терпим.
8. заголовки всех частей читаются параллельно, до 8 потоков (метка и2), функцией `st_header_remote()`. у больших моделей частей десятки, и по одной это заняло бы заметное время.
9. `arch.describe()` разбирает конфиг и тензоры. любой сбой разбора (`KeyError`, `IndexError`, `TypeError`, `AttributeError`, `ArithmeticError`, `struct.error`, `SystemExit`) даёт ошибку "не удалось прочитать заголовки", а не падение (метка и3): `describe` видит чужие конфиги, а они бывают какие угодно. временная папка удаляется всегда.
10. причины отказа делятся на "лечится склейкой" (в тексте причины есть `merge`, тогда поле `склейка` равно `True`) и жёсткие. к жёстким добавляются: нет шаблона диалога, если семья не из ручной разметки `tmpl.py` (метка и4), и нет `tokenizer.json`.
11. по описанию `arch.py` считаются размеры модели и байты кэша разговора на одну позицию (метка и5).
12. результат сохраняется в кэш.

поля результата:

| поле | что |
|---|---|
| `repo`, `ссылка`, `когда` | имя, адрес страницы, время сбора |
| `закрыта`, `лицензия`, `загрузок`, `нравится`, `изменена`, `задача` | из api |
| `файлов`, `байт_весов`, `байт_всего`, `кусков` | по отобранным файлам |
| `шаблон`, `токенизатор` | есть ли шаблон диалога (отдельный файл или `chat_template` в `tokenizer_config`) и есть ли `tokenizer.json` |
| `всего_параметров`, `типы`, `основной` | из блока `safetensors` в api: всего параметров, сколько по каждому типу, самый частый тип |
| `семья`, `слоёв`, `ширина`, `mlp`, `голов`, `kv`, `словарь`, `полных` | из описания `arch.py` (`kv` берётся у первого слоя, `полных` это число слоёв с полным вниманием) |
| `параметров` | элементы тензоров под `prefix` текстовой части плюс выходная матрица |
| `параметров_слоёв` | элементы тензоров под `layer_prefix` |
| `связана_головка`, `сводка` | связаны ли выход и эмбеддинги, строка `arch.summary` |
| `kv_на_позицию` | байт кэша k и v разговора на одну позицию: сумма по слоям `2 * hd * nkv * 4` (k и v в fp32) |
| `контекст` | `max_position_embeddings` |
| `поддержка`, `почему`, `склейка` | итог, причины, лечится ли склейкой |
| `ошибка` | если что то не вышло |

### заголовок по сети (`st_header_remote`, метки ж1, ж2, ж3)

заголовок safetensors это 8 байт длины (little endian) и потом json. первый запрос просит байты `0..HEAD1-1`, обычно заголовок целиком в них помещается. читается не больше `HEAD1` байт, даже если сервер не учёл `Range` и отдаёт весь файл. длина должна быть от 2 байт до 200 миб, иначе ошибка. если заголовок длиннее первого куска, делается второй запрос `8..7+n` с таймаутом 60 секунд. ключ `__metadata__` выбрасывается, результат имеет вид `{имя: (dtype, shape)}`.

### сеть (`_req`, `_json`)

заголовки запроса: `User-Agent: TierLM`, `Authorization: Bearer <ключ>`, если ключ есть, и `Range`, если нужен кусок файла. таймаут по умолчанию 20 секунд. `HTTPError` (ответ сервера с кодом) пробрасывается сразу. при других ошибках соединения, если какой нибудь прокси задан со схемой `https://`, запрос повторяется напрямую без прокси (метка г1): urllib не умеет прокси со схемой https, и соединение рвётся сразу. для повтора создаётся новый объект запроса, потому что обработчик прокси уже переписал адрес в старом (метка г2). `_json` просто читает ответ и разбирает json.

### каталог (`catalog`, метки л2 и дальше)

`catalog(search, sort, limit, org, min_b, max_b, tasks, token, offline, fresh)` возвращает `{"rows", "источник", "ошибка", "ещё", "когда"}` (метка ц1). сеть нужна только за самим списком. поле `поддержка` дописывает `mark()` из кэша, а решает его `check()` отдельно.

1. нормализация: неизвестный порядок становится `downloads`, `limit` не меньше 1 и без верхней границы, потому что продолжение дочитывается с места остановки (метка ц2). если в поиске ссылка или имя репозитория, оно приводится к виду `org/name`. запись `google/gemma` значит автор google, в названии gemma (метка ц3).
2. если есть кэш этого запроса, не задан `fresh` и (включён режим без сети или кэш моложе `TTL[sort]`), отдаётся кэш, источник "кэш".
3. иначе, если сеть недавно не ответила (`_down`), в сеть не идём. если идти можно, для каждого `pipeline_tag` из `tasks` параллельно зовётся `_fetch()`, строки сливаются и сортируются `_by()`, результат сохраняется, источник "сеть". при ошибке сети `_down[0]` ставится на 60 секунд вперёд.
4. если из сети не вышло: устаревший кэш этого же запроса (источник "кэш (устаревший)"), а если его нет, `_offline()`. в поле `ошибка` пишется причина и что показано вместо свежего списка.
5. в конце строки копируются и размечаются `mark()`. копия нужна, чтобы разметка не меняла строки, сохранённые в кэше и в `_CUR`.

`_fetch(task, ...)` (метка у1): запрос `<HF>/api/models` с параметрами `pipeline_tag`, `filter=safetensors`, `sort`, `direction=-1`, `limit=100`, `search`, `author` и `expand[]` по полям `EXPAND`. страница всегда полная, по 100 строк, потому что фильтр по размеру делается у клиента (метка у2). страницы читаются по ссылке `rel="next"` из заголовка `Link`, пока не наберётся `limit`, не кончатся страницы или не будет прочитано 50 страниц за один вызов (метка у3): так ответ не приходится ждать минутами, а дальше список дочитает следующее "ещё". пропускаются повторы, отключённые модели (`disabled`) и модели не того размера (при фильтре по размеру размер должен быть известен). состояние `(строки, ссылка на следующую страницу)` сохраняется в `_CUR`, и следующий вызов с большим `limit` дочитывает с места остановки, а не с начала (метка т2). ключ `_CUR` это `(search, sort, org, min_b, max_b)`, без `limit`. возвращает первые `limit` строк и признак, есть ли за ними ещё.

`_page(url, token)` (метка т1): одна страница и ссылка на следующую. адрес должен начинаться с `<HF>/api/`, иначе ошибка, и ссылка на следующую страницу тоже принимается только такая. так ключ уходит только на адрес hugging face. ответ, который не является списком, тоже ошибка.

`_row(m)` (метка с1): строка списка из ответа api: `repo`, `загрузок`, `нравится`, `тренд`, `изменена`, `создана`, `закрыта`, `задача`, `всего_параметров`, `типы`, `тип_модели`, `архитектуры`.

`_by(rows, sort)`: сортировка по убыванию поля из `SORTKEY`. у дат пустое значение считается пустой строкой, у чисел нулём.

`_offline(...)` (метка х1): сети нет. собираются все сохранённые списки `catalog_*` и все сохранённые сведения о моделях, по каждому репозиторию побеждает более свежая запись, а сведения о модели накладываются поверх строки из списка. если не нашлось ничего, берётся `SEED` (источник "запасной список", это не источник истины). дальше идёт тот же фильтр: все слова поиска должны встретиться в имени, автор должен совпасть, размер должен попасть в границы. порядок тот же, что и в сети.

### пометки и проверка поддержки

`known_all()` (метка м1): словарь пометок `{repo.lower(): {repo, проверка, заметка}}` из `hub_known.json`. файл перечитывается, только если у него сменилось время изменения. `known(repo)` даёт пометку или `{"проверка": "нет", "заметка": ""}`.

`cached_info(repo, max_age)` (метка о1): то, что `info()` уже узнал и сохранил, или `None`, если сведений нет, они устарели или в них ошибка.

`mark(rows, max_age=30 суток)` (метка п1): дописывает к строкам списка без сети:

1. `проверка` и `заметка`. заметка собирается из пометки и текста "требуется согласие на сайте" для закрытых моделей.
2. `поддержка`: `True` или `False`, если решено по заголовкам, `None`, если ещё не проверено или проверить не вышло.
3. поля `SHOW` из кэша сведений и уточнённое `закрыта`.
4. `проверка_ошибка`, если проверка этой модели недавно не удалась (текст держится 10 минут) или сеть сейчас считается недоступной.

строка меняется на месте: сначала убираются поля, которых в новой разметке нет, потом одно `update` (метка п2). снимать всё и дописывать заново нельзя, потому что строку в это время может читать окно.

`check(repos, token, workers=6, cb, cancel, fresh)` (метка р1): решает `поддержка` для репозиториев через `info(max_shards=16)`, не больше `workers` запросов сразу. если сеть только что не отвечала, ничего не делает, чтобы не ждать таймаут на каждой модели (метка р2). проверяются только модели без свежего кэша (или все при `fresh`), повторы в списке отбрасываются. `cb(repo, сведения)` вызывается по мере готовности, `cancel()` возвращает `True`, чтобы бросить недоделанное. любое исключение одной модели ловится и превращается в ошибку (метка р3): сбой одной модели не должен ронять остальные. неудачи запоминаются в `_bad`, удачная проверка убирает запись. возвращает число проверенных.

`main_list(a)` (метка ч1): разбор ключей, потом до 6 попыток: каталог, проверка (если не задан `--no-check`, не задан `--offline` и сеть не считается недоступной), разметка. если задан `--supported`, подходящих меньше `--limit`, продолжение есть и источник "сеть" или "кэш", `limit` удваивается и попытка повторяется (метка ч2). уже проверенное лежит в кэше и не пересчитывается.

### прогноз (`forecast`, метки ч3 и дальше)

`forecast(m, hw)` (метка аб1): `m` это результат `info()`, `hw` это словарь машины, который `tierlm.py` собирает в `hw_now()`:

| ключ | что |
|---|---|
| `ram`, `vram` | объём озу и видеопамяти, байты |
| `disk_free` | свободно на диске, байты |
| `pcie_gen`, `pcie_width` | поколение и ширина шины карты |
| `tier1` | сколько чисел обучаемой части помещается в бюджет видеопамяти |
| `anchor_step` | замер шага обучения: `(секунды, байт слоёв, имя запуска)` |
| `anchor_tok` | замер разговора: `(секунд на токен, байт слоёв, подпись замера)` |
| `есть_байт` | сколько уже лежит в папке модели |
| `disk_path` | необязательный: путь, по диску которого оценивать скорость чтения. без него берётся текущий каталог |

возвращает список строк для окна `(что, оценка, как считали, вид)`, где вид это `ok`, `warn` или `bad`. если в `m` нет `параметров`, список пустой.

вспомогательные функции и константы:

1. `LANE` (метка ч4): гигабайт в секунду на одну линию pcie по поколению: 1: 0.25, 2: 0.5, 3: 0.985, 4: 1.969, 5: 3.938, 6: 7.563.
2. `pcie_gbs(gen, width)` (метка ш1): если поколение или ширина не переданы, они берутся из замера шины главной карты `hwprobe.pcie()`. возвращает `линия * ширина * 0.8` байт в секунду и признак, известна ли шина. если поколение так и неизвестно, берётся 4.0 x16.
3. `QBYTES`: байт на параметр: `BF16` 2, `Q8_0` `34/32`, `Q6_K` `210/256`, `Q5_K_M` 0.71, `Q4_K_M` 0.6.
4. `reserve(ram)` (метка э1): сколько озу не отдавать под кэш замороженных весов. считается так же, как в движке, через `hwprobe.ram_reserve_now()`: что уже занято системой и другими программами, доля, которая всегда остаётся свободной по потолку памяти, и собственные нужды процесса. без `hwprobe` действует запасное правило: системе четверть озу, но от 5 до 8 гиб. всё остальное идёт под кэш весов.
5. `dims_of(m)` (метка ю1): размеры модели из `info()` в виде, который ждёт `hwprobe` (`hidden`, `inter`, `heads`, `layers`, `kv_per_pos`). если в сведениях нет `kv_на_позицию`, байты на позицию считаются по ширине головы `ширина / голов` и числу голов `kv`. если размеров нет совсем, возвращается пустой словарь.
6. `train_margin(vram, d)` (метка я1): видеопамять под активации шага обучения. берётся наибольшая упаковка, чьи активации помещаются в свою долю видеопамяти (`vram // TRAIN_ACT_SHARE`), так же, как её выбирает автопилот, а если не помещается и наименьшая, то `PACK_LO`. без размеров или без `hwprobe` 1.5 гиб.
7. `chat_margin(vram, d, ctx_max)` (метка аа1): видеопамять под кэш k и v разговора. окно контекста берётся так, чтобы кэш занял четверть видеопамяти, но не больше всего окна модели, с округлением вниз до кратного 256 и не меньше 256 позиций. так же контекст выбирает `chat.py`. без размеров 1 гиб.
8. `gib(n)` форматирует байты как гиб с одним знаком после точки.

расчёт по строкам (`PL` это `параметров_слоёв`, `lay = PL * 2` это слои в bf16, метка аб2):

1. диск: нужно `байт_всего - есть_байт` (то, что уже лежит в папке, второй раз не качается, метка аб3), плюс ещё раз `байт_весов`, если частей больше одной или нужна склейка: на время объединения нужна вторая копия. `ok`, если свободно больше нужного плюс 2 гиб, иначе `bad`.
2. озу при обучении: `cache = ram - reserve(ram)`. если `cache >= lay`, весь кэш весов в озу, иначе остаток читается с диска на каждом шаге (`warn`).
3. озу в разговоре: первый формат из `BF16`, `Q8_0`, `Q6_K`, `Q5_K_M`, `Q4_K_M`, который помещается в `cache`. если не помещается даже `Q4_K_M`, вид `bad`.
4. обучаемая доля: `min(1, tier1 / PL)` от строк каждой матрицы, `ok` от одного процента.
5. шаг обучения. сначала считается, что из замороженных весов может лежать в видеопамяти при обучении: `res = vram - train_margin - tier1 * 12 байт` (метка аб4). если есть замер `anchor_step`, его время масштабируется по объёму, который идёт по шине: `a0 * max(0.05, (lay - min(lay, res)) / max(1, a1 - min(a1, res)))`. если замера нет, `2 * (lay - res) / bw + 0.3` секунды, потому что веса идут по шине дважды за шаг. если кэш озу меньше `lay`, добавляется `2 * (lay - cache) / dbps` (метки аб5, аб6, аб7): `dbps` это скорость чтения диска из `hwprobe.disk_read_bps()`, то есть последний замер чтения весов движком или оценка по виду диска, а без `hwprobe` 2.5 гигабайта в секунду. `ok`, если шаг короче 15 секунд.
6. разговор в bf16: разговор держит в видеопамяти сколько влезет, `cres = vram - chat_margin` (метка аб8), по шине на каждый токен идёт `stream = lay - cres`. если есть замер `anchor_tok` (метка аб9), секунды на токен масштабируются по `stream`, `ok`, если быстрее 4 токенов в секунду. если замера нет, показывается верхняя граница `bw / stream` токенов в секунду. если `stream` равен 0, все веса в видеопамяти и шина скорость не ограничивает.
7. квантованная база `Q4_K_M`: показывается, если что то идёт по шине. сколько гиб она займёт и помещается ли целиком в видеопамять.

## 4. что важно знать, когда правишь

1. `info()` и `check()` ничего не бросают наружу: всё уходит в поле `ошибка`. окно на это рассчитывает. если добавляешь вызов, который может упасть на чужом конфиге, его исключение надо добавить в список ловимых.
2. ключ hugging face должен уходить только на адрес `HF`. все адреса строятся от `HF`, а ссылка продолжения проверяется в `_page()`. не принимай адреса из ответа сервера без такой проверки.
3. `HF` вычисляется при импорте. если поменять `HF_ENDPOINT` после импорта, модуль этого не увидит.
4. кэш сведений действует сутки для `info()` и `check()`, а `mark()` показывает сведения до 30 суток. то есть в списке может стоять старое решение о поддержке, пока проверка его не обновит.
5. записи с `ошибка` в кэше никогда не считаются годными, они только перезаписываются.
6. `_down` и `_bad` живут в памяти процесса. в командной строке они начинаются заново с каждым запуском, в окне держатся, пока работает программа.
7. в `_CUR` ключ без `limit`, поэтому "ещё" продолжает уже начатый список. `fresh` начинает с начала.
8. такой же список нужных файлов, как `KEEP`, есть в `fetch_model.sh`. если меняешь, что движку нужно из репозитория, правь оба места.
9. `reserve()`, `train_margin()` и `chat_margin()` должны считать так же, как движок, автопилот и `chat.py`. для этого они зовут `hwprobe.py`, где эти правила записаны один раз. если правило поменяется только в одном месте, прогноз начнёт расходиться с тем, что программа делает на самом деле.
10. каждый вызов `hwprobe` обёрнут в `try` с запасным значением: прогноз должен строиться и без замеров машины.
11. размеры в прогнозе берутся по `параметров_слоёв` в bf16 (2 байта на параметр), эмбеддинги в расчёт шага и разговора не входят.
12. `SEED` только запасной список на случай, когда нет ни сети, ни сохранённых ответов. настоящие пометки должны жить в `hub_known.json`.
13. `mark()` меняет строки на месте и может работать одновременно с окном, которое их читает. не заменяй строку целиком и не очищай её перед заполнением.
