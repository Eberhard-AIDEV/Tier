# hwprobe.py

## 1. что это за файл и за что он отвечает

hwprobe.py разбирает машину по тому, что система отдаёт сама (sysfs, kfd, `nvidia-smi`, `/proc`, `PATH`), и по правилам, а не по списку карт, решает, под какую архитектуру собирать движок, нужен ли `HSA_OVERRIDE_GFX_VERSION`, есть ли bf16 и сколько озу не отдавать под кэш весов. кроме этого он даёт замеры для прогнозов окна и для настройки обучения: шину карты, свободную видеопамять, датчики температуры карты, скорость чтения диска, размер упаковки шага. ещё он умеет сам поставить недостающее: модули python через пакеты дистрибутива или pip, компиляторы и библиотеки через системный пакетный менеджер. пользователю не предлагается ставить это руками.

файл работает двумя способами: как программа с ключами командной строки и как модуль, который импортируют другие части проекта.

кто его вызывает:

1. `build.sh`: `eval "$(python3 hwprobe.py --env)"` в начале сборки, берёт оттуда `TIER_VENDOR`, `TIER_ARCH`, `TIER_GPU_ARCH`, `HSA_OVERRIDE_GFX_VERSION`, `TIER_ARCH_ERR`, `TIER_BF16`. если нет `hipcc` или `nvcc`, зовёт `hwprobe.py --deps`. после сборки пишет вывод `hwprobe.py --fingerprint` в файл `<движок>.hw`.
2. `pydeps.sh`: просто `exec hwprobe.py --deps`.
3. `train.sh` и `auto.sh`: `hwprobe.py --pack P99 ПРИМЕРОВ МОДЕЛЬ`, когда размер упаковки шага не задан руками.
4. `tierlm.py`: `hwprobe.fingerprint()` сравнивается с содержимым `<движок>.hw`. если отпечаток другой, значит карта сменилась или обновился rocm, и собранный движок к этой машине не подходит. ещё берёт `temp_sensors()` для показа датчиков карты.
5. `ui.py`: `pcie()` и `temp_sensors()` для карты, выбранной в окне.
6. `hub.py`: `pcie()` для прогноза скорости подкачки по шине, `ram_reserve_now()` для резерва озу, `pack_fit()`, `act_bytes()`, `TRAIN_ACT_SHARE`, `PACK_LO` для оценки видеопамяти под активации, `disk_read_bps()` для прогноза времени чтения весов.
7. `replay.py`: `arch_dims()`, `vram_free_mib()`, `pack_fit()` и `EVAL_ACT_SHARE` для упаковки прохода оценки.
8. `chat.py`: `arch_dims()` (поле `kv_per_pos`) и `vram_free_mib()`, чтобы выбрать длину контекста, когда её не задали.

что вызывает сам: из файлов проекта только `arch.py`, и то лишь в `arch_dims()`, когда у папки модели нет `tier_arch.txt`. снаружи запускает `nvidia-smi`, `nvcc --version`, `hipconfig --rocmpath`, `pip`, `pacman`, `apt-get`, `pkexec`, `sudo`. читает `~/.config/tier.conf`, который пишет движок, и журналы запусков в рабочей папке.

## 2. как он работает

### ключи командной строки

```
python3 hwprobe.py --json
python3 hwprobe.py --env
python3 hwprobe.py --deps
python3 hwprobe.py --fingerprint
python3 hwprobe.py --pack P99 ПРИМЕРОВ [tier_arch.txt или папка модели]
```

1. без ключей и с `--json`: печатает json `{"факты": ..., "конфигурация": ...}`, где факты это всё собранное, а конфигурация это те же пары, что и в `--env`.
2. `--env`: строки `ПЕРЕМЕННАЯ=значение` для `eval` в `build.sh`.
3. `--deps`: ставит недостающее, потом собирает факты заново. если других ключей нет, выходит с кодом 0, когда всё есть, и 1, когда чего то не хватает. можно совмещать с `--env` и `--json`, тогда после установки печатается вывод.
4. `--fingerprint`: печатает отпечаток и выходит с кодом 0.
5. `--pack`: печатает одно число, размер упаковки шага обучения (0, 512, 1024 и дальше степенями двойки), и выходит. `P99` это длина примера в токенах, которую не превышают 99 процентов набора, `ПРИМЕРОВ` это число примеров. третий довод необязателен: файл `tier_arch.txt` или папка модели. если доводов меньше двух, программа выходит с сообщением о формате вызова. этот ключ проверяется первым и машину целиком не опрашивает: смотрит только свободную видеопамять и размеры модели.

во всех остальных режимах сначала один раз вызывается `facts()`, то есть машина опрашивается всегда, даже для `--fingerprint`.

### переменные окружения

| переменная | смысл | по умолчанию |
|---|---|---|
| `HWPROBE_ROOT` | префикс к путям, которые читает `rd()`, и к поиску в sysfs. нужен для проверки на поддельном дереве каталогов | пусто, то есть настоящий корень |
| `ROCM_PATH` | корень rocm для поиска каталогов ядер и заголовка hipblaslt | вывод `hipconfig --rocmpath`, иначе `/opt/rocm` |
| `ROCBLAS_TENSILE_LIBPATH` | дополнительный каталог ядер rocblas, проверяется первым | нет |
| `TIER_CONF` | путь к файлу настроек движка | `~/.config/tier.conf` |
| `TIER_RAM_OTHER_GIB` | собственные нужды процесса в гиб для расчёта резерва озу | 1 гиб |
| `WORK`, `D` | рабочая папка с журналами запусков для `disk_read_bps()` | из `settings.json` окна |
| `TIER_DATA`, `XDG_DATA_HOME` | где искать `settings.json` окна | `~/.local/share/tierlm` |

`HWPROBE_ROOT` не действует на `shipped()` и `shipped_any()` (каталоги ядер), на проверку заголовка hipblaslt, на `shutil.which`, на запуск внешних программ и на поиск диска в `_block_of()`.

### что пишется в `--env`

| переменная | откуда | смысл |
|---|---|---|
| `TIER_VENDOR` | главная карта | `amd` или `nvidia` |
| `TIER_ARCH` | у amd `сборка_для` (или сама архитектура), у nvidia `sm_<cc>` | под что компилировать |
| `TIER_GPU_ARCH` | у amd настоящая архитектура карты | для сообщений сборки |
| `HSA_OVERRIDE_GFX_VERSION` | у amd, если собираем под донора | что сказать рантайму, какая это карта |
| `TIER_ARCH_ERR` | у amd, если нет ни своих ядер, ни донора | текст отказа в одинарных кавычках для `eval`, одинарные кавычки внутри текста вырезаются |
| `TIER_BF16` | правила карты | 1 или 0 |
| `TIER_DT` | правила карты | `bf16` или `fp16`. без bf16 берётся fp16, а есть ли умножение fp16 на fp32, проверяет сам движок (ключ `fp16gemm` в `tier.conf`) |
| `TIER_RESERVE_RAM` | `ram_reserve_now()` | сколько байт озу не отдавать под кэш весов |

переменные для nvidia пишутся, только если известен `cc`, для amd только если известна архитектура. `TIER_BF16`, `TIER_DT`, `TIER_RESERVE_RAM` пишутся всегда.

### поток

1. `facts()` собирает: процессор, озу, карты из drm (с шиной), узлы kfd, карты nvidia, инструменты, дистрибутив, главную карту (`decide`), резерв озу, чего не хватает (`missing`).
2. `decide()` выбирает главную карту и правила для неё.
3. дальше по ключу: вывод json, вывод env, установка или отпечаток.

функции замеров (`pcie`, `temp_sensors`, `vram_free_mib`, `disk_read_bps`, `pack_choice` и соседние) живут отдельно от этого потока: их зовут другие модули напрямую, когда нужен свежий замер.

### структура фактов (json)

ключи словаря `факты`: `процессор` (модель, ядра, флаги avx2, fma, avx512), `ОЗУ` (`всего`, `доступно` в байтах), `видеокарты_drm`, `kfd`, `nvidia`, `инструменты`, `дистрибутив` (`arch`, `debian` или пусто), `главная`, `резерв_ОЗУ`, `нехватает` (`python`, `компилятор`, `системное`).

## 3. главные функции и разделы

### мелкие помощники

`p(path)` ставит `HWPROBE_ROOT` перед путём. `rd(path, d)` читает файл целиком, обрезает пробелы, при ошибке возвращает `d`. `sh(*cmd, t=8)` запускает команду с таймаутом 8 секунд и отдаёт stdout только при коде 0, иначе пустую строку. `have(name)` есть ли программа в `PATH`. `num(s)` первое число в начале строки, иначе 0.

### факты о машине

1. `cpu()`: первая строка `flags` и `model name` из `/proc/cpuinfo`, число ядер из `os.cpu_count()`.
2. `ram()`: `MemTotal` и `MemAvailable` из `/proc/meminfo`, перевод из киб в байты.
3. `gpus_drm()`: карты из `/sys/class/drm/card*/device` без вызова утилит. берутся только вендоры `0x1002` (amd) и `0x10de` (nvidia). читаются `mem_info_vram_total`, `mem_info_vram_used`, `mem_info_gtt_total` (эти файлы есть у драйвера amdgpu). в поле `шина` лежат `поколение` и `линий` из `pcie()`, а рядом сырые текущие и максимальные скорость и ширина самой карты.
4. `kfd_nodes()`: для каждого узла `/sys/class/kfd/kfd/topology/nodes/*` читается `gfx_target_version`. узлы без него (процессор) пропускаются. архитектура собирается как `gfx%d%d%x` из `v//10000`, `v//100 % 100` и `v % 100`, последняя цифра шестнадцатеричная. например 90500 даёт gfx950, 90012 даёт gfx90c. память узла это сумма `size_in_bytes` по `mem_banks` с `heap_type` 1 или 2 (видеопамять, видимая и не видимая процессору).
5. `nvidia()`: одна строка на карту из `nvidia-smi --query-gpu=name,memory.total,compute_cap,driver_version,pcie.link.gen.current,pcie.link.width.current`. память в миб переводится в байты, `cc` записывается без точки (8.6 становится 86).
6. `toolchain()`: версия rocm из `/opt/rocm/.info/version` или `/opt/rocm/share/doc/hip/version`, версия cuda из `nvcc --version`, есть ли `hipcc`, `nvcc`, `rocminfo`. заголовок `include/hipblaslt/hipblaslt.h` ищется в корне rocm (`rocm_root()`) и в `/usr`, так же, как его ищет `build.sh`: rocm из пакетов дистрибутива лежит в `/usr`.
7. `python_pkgs()`: каких модулей нет из `tokenizers`, `numpy`, `jinja2` (проба импортом).
8. `distro()`: по `ID` и `ID_LIKE` из `/etc/os-release`: `arch`, `debian` (сюда же ubuntu) или пусто.

### карта, шина и датчики

1. `gpu_dev(pci_or_card)`: каталог pci устройства карты в sysfs. довод может быть адресом pci, именем вида `card1` или готовым путём в `/sys/`. без довода берётся карта amd или nvidia с наибольшей видеопамятью по `mem_info_vram_total`. этой функцией пользуются все замеры ниже, поэтому окно может спросить про конкретную карту, а прогноз про главную.
2. `pcie(pci)`: пара `(поколение, линий)` шины карты. берётся узкое место всей цепочки от карты до корневого порта: путь устройства в sysfs проходится вверх по родителям, пока у звена есть `max_link_speed`, и на каждом звене учитываются наибольшие договорные скорость и ширина (`max_link_speed`, `max_link_width`). итог это наименьшее поколение и наименьшая ширина по цепочке. так сделано по двум причинам. у части карт внутри стоит свой коммутатор, и сама карта показывает более быструю шину, чем даёт слот, поэтому смотреть только на карту нельзя. текущая скорость в простое падает до самой низкой ради энергосбережения и о пропускной способности под нагрузкой не говорит, поэтому берутся максимальные значения. скорость в гт на линию переводится в поколение по таблице `GT`: от 63 это 6, от 31 это 5, от 15 это 4, от 7 это 3, от 4 это 2, остальное 1. если sysfs ничего не дал, а `nvidia-smi` есть, берутся `pcie.link.gen.max` и `pcie.link.width.max`. если ничего не известно, ответ `(0, 0)`.
3. `temp_sensors(pci_or_card)`: список датчиков температуры карты, каждый словарь `{label, now_c, crit_c, emerg_c}` в градусах цельсия. у amd читаются все `temp*_input` в `hwmon` карты, подпись из `temp*_label` (если её нет, имя датчика), порог замедления из `temp*_crit`, порог аварийного отключения из `temp*_emergency`. значения в sysfs в тысячных долях градуса, функция делит их на 1000. у nvidia, если hwmon пуст, текущая температура берётся из `nvidia-smi --query-gpu=temperature.gpu`, а пороги из `nvidia-smi -q -d TEMPERATURE` (строки замедления и отключения). для конкретной карты nvidia в `nvidia-smi` передаётся `-i` с её адресом. порога нет, значит `None`.
4. `vram_free_mib(pci_or_card)`: свободная видеопамять карты сейчас в миб. у amd это разность `mem_info_vram_total` и `mem_info_vram_used` из sysfs, у nvidia `memory.free` из `nvidia-smi`. неизвестно, значит 0.

### правила выбора сборки

1. `gfx_parse(arch)`: `gfx1032` даёт `(10, 3, 2)`, `gfx90c` даёт `(9, 0, 12)`, `gfx942` даёт `(9, 4, 2)`. старшие цифры это поколение, две последние шестнадцатеричные. не похоже на имя архитектуры, значит `None`.
2. `rocm_root()`: `ROCM_PATH`, иначе вывод `hipconfig --rocmpath`, иначе `/opt/rocm`. берётся, только если такой каталог существует.
3. `shipped(lib)`: для каких архитектур установленная библиотека (`rocblas`, `hipblaslt` и другие) поставляет готовые ядра. смотрятся каталоги `<rocm>/lib/<lib>/library`, `/usr/lib*/<lib>/library` и `/usr/lib*/*/<lib>/library` (так раскладывает debian), для rocblas первым ещё `ROCBLAS_TENSILE_LIBPATH`. из имён файлов вынимается всё вида `gfx` плюс цифры. результат множество имён архитектур.
4. `shipped_any()`: запасной список архитектур, когда каталога ядер rocblas нет. собирается через `shipped()` по `hipblaslt`, `hipsparselt`, `rocsparse`, `rocfft`, `miopen`, `rocsolver` и обходом `<rocm>/lib`, `/usr/lib*/rocm` и `/usr/share/miopen` на глубину до трёх уровней с тем же разбором имён файлов. смысл: под какие архитектуры собран установленный rocm в целом.
5. `amd_group(t)`: семейство набора команд. внутри семейства код одной архитектуры исполняется на другой, на этом и стоит `HSA_OVERRIDE_GFX_VERSION`. правила:
   1. 9.0 со степпингом 8 или 10 (gfx908, gfx90a) это `cdna1-2`, остальные 9.0 (gfx900, gfx902, gfx904, gfx906, gfx909, gfx90c) это `gcn5` (vega).
   2. все 11.x (gfx110x и gfx115x) считаются одним набором `rdna3`.
   3. остальные по `поколение.версия`: 9.4 cdna3, 9.5 cdna4, 10.1 rdna1, 10.3 rdna2, 12.0 rdna4.
6. `amd_rules(arch, lib)`: под что собирать и нужен ли override, по тому, для каких архитектур установленный rocblas поставляет ядра. без ядер rocblas для архитектуры движок падает на первом умножении матриц, поэтому порядок такой:
   1. bf16 включается для поколения 11 и выше и для 9.x с версией 4 и выше или степпингом 10 (rdna3 и дальше, cdna2 и дальше). это только предварительное решение, окончательно решает проба в самом движке.
   2. если своя архитектура есть в списке rocblas, собираем под неё без подмены.
   3. если каталог ядер rocblas вообще не найден, список донорских архитектур берётся из `shipped_any()`, а в поле `замечание` пишется, что донор определён по ядрам других библиотек rocm. если и этот список пуст или в нём есть своя архитектура, собираем под свою без подмены.
   4. дальше ищется донор: архитектура из списка того же семейства. порядок выбора: сначала с теми же поколением и версией, потом со степпингом 0, потом с ближайшим степпингом, потом по имени. override пишется как `поколение.версия.степпинг` десятичными числами.
   5. если донора нет, а список был взят у других библиотек, отказа нет: собираем под свою архитектуру, а работает ли она, покажет проба движка. по чужим библиотекам отказывать нельзя.
   6. если донора нет в настоящем списке rocblas, `сборка_для` пустой, а в поле `нет_ядер` текст отказа: нужен rocm с поддержкой этой архитектуры или старшей в семействе.
   7. поле `hipblaslt_ядра` говорит, есть ли ядра hipblaslt для своей архитектуры. это сведение, на выбор сборки оно не влияет.
7. `nv_rules(cc)`: cc 80 и выше: bf16 и тензорные ядра, cuda от 11.0. cc от 70 до 79: тензорные ядра без bf16, путь fp16 и fp32. ниже 70: без bf16 и тензорных ядер, движку нужен путь fp32, в поле `нужен_cuda` 11.8 для cc от 35 и 10.2 для более старых.
8. `decide(f)`: кандидаты это все узлы kfd, все карты `nvidia-smi` и карты amd из drm (последние только если kfd не дал ни одной карты amd, тогда архитектура пустая с замечанием). главная карта та, где больше памяти, так встроенная графика рядом с дискретной картой не становится главной. аргумент `f` не используется. в результат добавляются `вендор`, `память`, `вендоров_видно`. карт нет совсем, значит `вендор` пустой и замечание.

### резерв озу

1. `conf(key, d)`: значение ключа из `tier.conf` (путь из `TIER_CONF` или `~/.config/tier.conf`). файл пишет движок при осмотре машины, формат строк `ключ значение`. если `d` число, ответ тоже число, иначе строка. файла или ключа нет, значит `d`.
2. `ram_reserve(total_bytes, avail_bytes, cap_pct, other_bytes)`: сколько озу не отдавать под кэш весов. это сумма трёх частей: что уже занято системой и программами (разность `MemTotal` и `MemAvailable`), доля, которая всегда остаётся свободной по потолку памяти (`100 минус cap_pct` процентов от всего озу, потолок зажат от 50 до 99, по умолчанию 98), и собственные нужды процесса (по умолчанию 1 гиб). правило то же, что у движка, поэтому прогноз в окне и поведение движка совпадают.
3. `ram_reserve_now()`: `ram_reserve()` по замеру прямо сейчас: `/proc/meminfo`, потолок из ключа `mem_cap_pct` в `tier.conf`, нужды процесса из `TIER_RAM_OTHER_GIB`, если задано.

### упаковка шага

упаковка это сколько токенов из нескольких примеров склеивается в один шаг обучения. чем она больше, тем меньше шагов на эпоху, но тем больше видеопамяти уходит под активации.

1. `act_bytes(pack, hidden, inter, heads, layers)`: оценка видеопамяти под активации шага на `pack` токенов, та же, что у движка: `P*(8*hidden + 3*inter)*4 + 2*heads*P*P*4 + layers*P*hidden*4` байт (fp32). квадратная часть это матрицы внимания, поэтому большая упаковка дорожает быстро.
2. `arch_dims(path)`: размеры модели для оценок: `hidden`, `inter`, `heads`, `layers`, `vocab` и `kv_per_pos`. источник `tier_arch.txt`: путь к самому файлу или к папке модели, где он лежит. если в папке его нет, описание строится через `arch.describe()` и `arch.text()` по `config.json`. строки `hidden`, `inter`, `heads`, `layers`, `vocab` дают числа, строки `layer i тип hd nkv` дают `kv_per_pos`: сумму `2*hd*nkv*4` по слоям, то есть сколько байт кэша kv разговора нужно на одну позицию при хранении k и v в fp32. если не хватает хотя бы одного из `hidden`, `inter`, `heads`, `layers`, ответ пустой словарь.
3. постоянные:
   1. `PACK_LO` 512: наименьшая упаковка. меньше нет смысла, тогда учим по одному примеру на шаг (упаковка 0).
   2. `PACK_CAP` 16320: строка внимания упаковки должна поместиться в разделяемую память блока (64 киб, fp32, запас 64).
   3. `TRAIN_ACT_SHARE` 8: активации шага обучения занимают не больше восьмой части свободной видеопамяти, остальное нужно обучаемой части, подкачке весов и буферам.
   4. `EVAL_ACT_SHARE` 2: при оценке нет обратного прохода и состояния adam, поэтому активациям можно до половины свободной видеопамяти.
4. `pack_fit(room_bytes, dims, lo, cap)`: наибольшая упаковка степенью двойки от `lo` до `cap`, чьи активации помещаются в `room_bytes`. не помещается даже `lo`, значит 0.
5. `pack_choice(p99, n_examples, vram_free_mib, dims)`: размер упаковки шага обучения. правила:
   1. маленький набор (до 256 примеров включительно): 0, по одному примеру. на таком наборе упаковка съедает сами шаги.
   2. наибольшая допустимая упаковка по карте: `pack_fit()` от восьмой части свободной видеопамяти. если размеров модели или свободной видеопамяти нет, наибольшей считается `PACK_LO`.
   3. желаемая упаковка: наименьшая степень двойки от 512, в которую входят хотя бы 2,5 примера длины p99, но не больше `PACK_CAP`.
   4. если желаемая помещается в допустимую, берётся она.
   5. иначе берётся наибольшая допустимая, если в неё входит пример длины p99 с запасом 28 процентов, а если не входит, 0.

### диск

1. `_log_speed()`: последний замер чтения весов движком. рабочая папка берётся из `WORK` или `D`, иначе из `settings.json` окна, иначе `work` в папке данных. среди файлов `*_log.tsv`, `*_console.txt`, `*_infer.log` просматриваются до 20 самых свежих, у каждого последние 8 миб, и ищется строка движка о кэше весов с объёмом в гиб, временем в секундах и скоростью в мб в секунду. крошечные чтения (меньше 0,5 гиб или быстрее 0,2 с) пропускаются: это служебные проходы, о диске они не говорят. ответ в байтах в секунду, ничего не нашлось, значит 0.
2. `_block_of(path)`: имя диска под путём (вида `nvme0n1` или `sda`). сначала через номер устройства файла в `/sys/dev/block`, с переходом от раздела к целому диску и через слои `slaves` (шифрование, lvm) до настоящего диска. если номер устройства не ведёт в sysfs (так бывает у btrfs), ищется самая длинная подходящая точка монтирования в `/proc/self/mountinfo` и её устройство.
3. `disk_read_bps(path)`: скорость чтения диска в байтах в секунду. если есть замер движка, берётся он. иначе оценка по виду диска под `path` (или текущей папкой): nvme около 2,5 гб в секунду, вращающийся около 150 мб в секунду, прочие ssd около 500 мб в секунду.

### что не хватает и установка

`missing(f)` собирает три списка:

1. `python`: модули, которые не импортируются.
2. `компилятор`: `rocm-hip-sdk`, если главная карта amd и нет `hipcc`, `cuda`, если главная nvidia и нет `nvcc`.
3. `системное`: `hipblaslt`, если карта amd и нет заголовка hipblaslt.

таблицы: `PYPKG` переводит модуль python в пакет дистрибутива (на arch `python-tokenizers`, `python-numpy`, `python-jinja`, на debian `python3-numpy`, `python3-jinja2`, tokenizers на debian пакетом нет). `PKG` переводит нужное в системные пакеты: на arch `rocm-hip-sdk`, `hipblaslt`, `cuda`, на debian только `nvidia-cuda-toolkit` для cuda, а для rocm и hipblaslt стоит `None`. где пакета в дистрибутиве нет, программа об этом сообщает и ничего не выдумывает.

`install(f, log)`:

1. модули python сначала пакетами дистрибутива (на arch и в новых debian pip в системный python не ставит), остальное через `pip install --user`, при неудаче ещё раз с `--break-system-packages`.
2. компиляторы и системное по `PKG`. если дистрибутив не распознан или пакета нет, пишется сообщение и пункт пропускается.
3. команда: на arch `pacman -S --needed --noconfirm`, на debian `apt-get install -y`.
4. если процесс не от root, перед командой ставится `pkexec`, если его нет, то `sudo -n` (без запроса пароля в терминале). если нет ни того, ни другого, печатается команда, которую надо выполнить с правами администратора.
5. если на debian установка не удалась, запускается `apt-get update`. повторной установки в этом же запуске нет.
6. возвращает список того, что не хватало до установки.

### отпечаток

`fingerprint()` это строка `вендор|архитектура или cc|версия rocm или cuda|первые 12 знаков sha1 от списка ядер rocblas`. смысл: под что собран движок. сменилась карта или обновился rocm, значит прежний движок и его `HSA_OVERRIDE_GFX_VERSION` к новой машине не подходят. `build.sh` пишет эту строку рядом с движком, `tierlm.py` сравнивает с текущей.

### вывод

`env_lines(f)` строит словарь переменных (таблица в разделе 2). `__main__` разбирает ключи: сначала `--pack`, потом `facts()`, потом `--deps`, `--fingerprint`, `--env`, иначе json.

## 4. что важно знать, когда правишь

1. правила должны оставаться правилами по признакам (поколение, семейство, что поставляет rocblas), а не списком конкретных карт. новая карта должна работать, если её семейство уже понятно.
2. формат `--env` читается через `eval` в `build.sh`. значения не должны содержать пробелов без кавычек и одинарных кавычек внутри. поэтому `TIER_ARCH_ERR` оборачивается в одинарные кавычки, а кавычки из текста вырезаются.
3. `build.sh` уважает переменные, которые пользователь задал сам: `TIER_VENDOR`, `TIER_ARCH`, `HSA_OVERRIDE_GFX_VERSION` из окружения перекрывают то, что выдал hwprobe.py.
4. отпечаток должен меняться ровно тогда, когда собранный движок перестаёт подходить. если добавить в него что то нестабильное (например занятую память), `tierlm.py` будет каждый раз считать движок чужим.
5. `ram_reserve()` и `act_bytes()` повторяют расчёты движка. если менять формулу, менять надо в обоих местах, иначе прогноз в окне и реальное поведение разойдутся.
6. вывод `--pack` читают `train.sh` и `auto.sh` как одно число. ничего, кроме этого числа, в stdout печатать нельзя.
7. поле `bf16` для amd это только предположение. движок сам проверяет, работает ли матричное bf16, и при неудаче выбирает запасной путь. для nvidia решение по cc окончательное.
8. при доноре из `shipped_any()` отказ не выдаётся никогда: это догадка, а не точное знание о ядрах rocblas.
9. `sh()` глотает все ошибки и даёт пустую строку. если утилита зависла, через 8 секунд просто нет данных, без исключения.
10. в `kfd_nodes()` файлы `mem_banks` открываются по пути, который уже содержит `HWPROBE_ROOT` (он пришёл из `glob` с префиксом), поэтому там стоит `open()`, а не `rd()`. то же в `pcie()`: путь звена уже с префиксом, и перед `rd()` префикс отрезается.
11. `decide()`, `toolchain()` и все замеры опрашивают систему при каждом вызове, кэша нет. `fingerprint()` вызывает их заново. кэшировать, если нужно, должен вызывающий (так делает окно для шины).
12. установка требует прав администратора и может спросить пароль через окно pkexec. `sudo -n` без настроенного доступа без пароля просто откажет.
