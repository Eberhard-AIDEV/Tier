# tier_wmma.h

## 1. что это за файл и за что он отвечает

tier_wmma.h это заголовок с собственным ядром матричного умножения для карт amd поколения rdna4 (архитектура gfx12). ядро работает на матричных блоках wmma 16x16x16 в волнах по 32 потока и делает одно конкретное умножение, которое движку нужно чаще всего: умножение x3.

умножение x3 устроено так. вес модели хранится в 16 битах (fp16 или bf16) и точен как есть. вход (активации) хранится в fp32, и если его просто округлить до 16 бит, точность упадёт. поэтому вход раскладывается на три части в 16 битах: старшую, среднюю и младшую, так что их сумма почти точно равна исходному числу fp32. результат считается как сумма трёх произведений: каждая часть входа умножается на один и тот же вес, а всё копится в fp32. по точности это выходит на уровне обычного умножения fp32, а работают быстрые блоки 16 бит.

библиотека hipblaslt умеет это делать только тремя отдельными вызовами, и каждый вызов заново читает весь вес из видеопамяти. своё ядро читает плитку веса один раз и сразу умножает её на все три части входа, копя результат в одних и тех же накопителях. вес обычно самая большая матрица в умножении, поэтому одно чтение вместо трёх и есть главный смысл файла.

файл подключается в `tier.cpp` строкой `#include "tier_wmma.h"` и отдельно не собирается. в сборке для cuda (когда определён `TIER_CUDA`) файл пустой целиком. в сборке для hip под другую карту, не gfx12, ядро собирается с пустым телом, а движок его не зовёт.

кто ещё знает про файл:

1. `build.sh`: включает его в хэш исходников движка, так что правка этого файла сама вызывает пересборку.
2. `tierlm.py`: перечисляет его в `ENGINE_SRC`, по этому списку программа проверяет, свежий ли собранный движок.
3. `pack.sh`: кладёт его в пакет вместе с остальными исходниками движка, потому что движок собирается на машине пользователя.

## 2. что считает ядро

в обозначениях ядра:

```
C[n x m] (+)= сумма по p от 0 до 2: X_p[n x k] * W[m x k]^T
```

1. `n` это число строк входа, то есть число токенов в упаковке.
2. `m` это число выходов слоя (строки матрицы веса).
3. `k` это ширина входа (общая размерность умножения).
4. `X` это три части входа подряд в памяти: сначала старшая, потом средняя, потом младшая. каждая часть это матрица `[n x k]`, где `k` идёт подряд, а шаг между частями равен `n*k` элементов.
5. `W` это вес `[m x k]`, `k` подряд. так лежит вес для прямого хода, `out = x * W^T`.
6. `C` это выход в fp32: строка на токен, шаг между строками `ldc`. при `acc1` равном 1 результат прибавляется к тому, что уже лежит в `C`, при 0 записывается поверх.

есть второй вид раскладки веса, параметр шаблона `TR`. тогда вес лежит как `[k x m]`, `m` подряд. так он нужен в обратном ходе по входу, `dX = dY * W`: вес тот же, а умножать надо без транспонирования. ядро в этом режиме читает вес по строкам и переставляет его на лету при записи в общую память, об этом ниже.

## 3. как устроен файл

### типы и операция блока

1. `f8` это вектор из 8 float, так выглядит накопитель одного потока для плитки 16x16 (256 чисел на 32 потока).
2. `u4` это вектор из 4 unsigned, то есть 16 байт. ими ядро читает и пишет память: 16 байт это 8 чисел по 16 бит за одно обращение.
3. `TW_GFX12` определяется, только когда код собирается под `gfx1200` или `gfx1201`. всё, что зовёт инструкции wmma, стоит под этим условием, иначе сборка под другие карты не прошла бы.
4. `Op<T>` это обёртка над одной инструкцией блока для двух типов: `Op<_Float16>` зовёт `__builtin_amdgcn_wmma_f32_16x16x16_f16_w32_gfx12`, `Op<__bf16>` зовёт `__builtin_amdgcn_wmma_f32_16x16x16_bf16_w32_gfx12`. у каждого есть тип `V`, вектор из 8 чисел 16 бит, это доля одного потока в операнде 16x16. ядро написано один раз через `Op<T>::mma` и работает для обоих типов.

### ядро `x3k`

шаблон `x3k<T, P, MR, NR, KT, TR>`:

1. `T` это тип 16 бит (`_Float16` или `__bf16`).
2. `P` это число частей входа, везде 3.
3. `MR` это сколько плиток 16 строк входа берёт одна волна.
4. `NR` это сколько плиток 16 столбцов выхода берёт одна волна.
5. `KT` это сколько плиток по `k` (по 16) лежит в общей памяти за один шаг, то есть шаг по `k` равен `16*KT`.
6. `TR` это раскладка веса, описанная выше.

#### блок и волны

блок это 256 потоков, 8 волн по 32. волны стоят сеткой 4 на 2: `MW=4` по строкам входа и `NW=2` по столбцам выхода. блок считает кусок выхода `BM x BN`, где `BM = 64*MR` строк токенов и `BN = 32*NR` столбцов. волна с номером `w` берёт плитки строк `wm + 4*i` и плитки столбцов `wn + 2*j`, где `wm = w/2`, `wn = w%2`. плитки волн перемежаются, а не лежат сплошными кусками, так все волны одинаково читают общую память.

у каждой волны массив накопителей `acc[MR][NR]` типа `f8`. все три части входа копятся в одни и те же накопители.

#### порядок блоков

сетка запуска: по `x` столбцы выхода (`m/BN` блоков), по `y` строки входа (`(n+BM-1)/BM` блоков). номер блока перекладывается группами по 8: подряд идущие блоки сначала проходят до 8 соседних кусков строк при одном куске столбцов, потом переходят к следующему куску столбцов. так одна плитка веса нужна нескольким блокам, которые работают одновременно, и чаще берётся из кэша карты, а не из видеопамяти.

#### общая память

общая память блока разбита на плитки 16x16 по 512 байт (256 чисел по 2 байта). сначала идут плитки входа: `P*MT*KT` штук, где `MT = BM/16`, по всем трём частям. за ними плитки веса: `NTL*KT` штук, где `NTL = BN/16`. макросы `TW_AT(mt,kt)` и `TW_BT(nt,kt)` дают адрес нужной плитки. общий размер `(P*BM+BN)*KT*32` байт.

главное в раскладке: внутри плитки данные лежат не по строкам матрицы, а в порядке операнда инструкции. поток `L` по адресу `L*16` находит ровно те 8 чисел, которые ему нужны для `mma`. поэтому чтение операнда из общей памяти это одно обращение по 16 байт на поток, без пересчёта адресов и без конфликтов банков.

#### загрузка из видеопамяти, `TW_GLOAD`

каждая из 8 волн грузит свою долю плиток: `TA = P*MT*KT/8` плиток входа и `TB = NTL*KT/8` плиток веса. проверка `static_assert` требует, чтобы плитки делились на волны без остатка. поток `L` берёт строку `L&15` плитки и половину по `k`: числа с `(L>>4)*8` по `(L>>4)*8+7`. это 16 байт, одно чтение `u4` в регистры `ga[]` и `gb[]`.

строки за концом упаковки (когда `n` не делится на `BM`) не проверяются ветвлением: номер строки обрезается до `n-1`, и поток читает последнюю настоящую строку. адрес законный, ветвлений в цикле нет, а лишние строки потом просто не пишутся в выход.

в режиме `TR` плитка веса читается иначе: два потока на строку `k`, каждый читает 8 соседних столбцов `m` этой строки. в памяти они лежат подряд, так что это тоже одно чтение 16 байт.

#### запись в общую память, `TW_SSTORE`

для входа и для веса без `TR` поток кладёт свои 16 байт по адресу `L*16` своей плитки, раскладка уже совпадает с порядком операнда.

в режиме `TR` поток держит 8 чисел одной строки `k` и разных `m`, а операнду нужен обратный порядок. поэтому поток пишет их восемью записями по 2 байта сразу на места, где они должны лежать в порядке операнда. так перестановка делается при записи в общую память за 8 записей на поток, а не отдельным проходом по весу.

#### счёт, `TW_COMPUTE`

для каждой плитки по `k` из `KT`: волна читает `NR` операндов веса для своих столбцов, затем для каждой из трёх частей и каждой своей плитки строк читает операнд входа и делает `NR` инструкций `mma` в накопители `acc[i][j]`. операнд веса читается из общей памяти один раз и идёт во все три части, а в видеопамять вес не уходит вовсе: он туда ходил один раз в `TW_GLOAD`.

#### барьер, `TW_BAR`

барьер написан вставкой на ассемблере: `s_wait_dscnt 0x0`, потом `s_barrier_signal -1` и `s_barrier_wait -1`. он ждёт только окончания операций с общей памятью, но не чтений из видеопамяти. это нужно, чтобы следующая порция данных из видеопамяти продолжала идти в регистры, пока волны считают и ждут друг друга. обычный барьер ждал бы и эти чтения, и вся подкачка заранее теряла бы смысл.

#### главный цикл

число шагов `nk = k/(KT*16)`. перед циклом первая порция грузится и кладётся в общую память. дальше на каждом шаге:

1. `TW_GLOAD` для следующей порции в регистры (чтения уходят и идут в фоне).
2. барьер, затем `TW_COMPUTE` по текущей порции в общей памяти.
3. барьер, затем `TW_SSTORE`: следующая порция из регистров в общую память.

после цикла последний барьер и счёт последней порции. так чтение из видеопамяти всегда перекрывается со счётом прошлой порции, а общей памяти нужен только один набор плиток.

внутри цикла стоят подсказки планировщику компилятора `__builtin_amdgcn_sched_group_barrier`. они задают порядок команд: сначала все чтения из видеопамяти (маска `0x020`), потом чтения из общей памяти (`0x100`) вперемешку с инструкциями блока (`0x008`) в том порядке, в каком их требует `TW_COMPUTE`, и в конце записи в общую память (`0x200`). без этого компилятор может собрать чтения из общей памяти в одну кучу перед счётом, и блоки будут простаивать.

#### запись результата

поток `L` держит в накопителе столбец `L%16` своей плитки 16x16 и строки с `(L/16)*8` по `(L/16)*8+7`. для каждой плитки и каждого из 8 чисел поток считает строку и столбец в `C` и пишет, только если строка меньше `n`. при `acc1` число прибавляется к старому значению `C`, иначе записывается поверх. столбцы не проверяются: `m` всегда делится на `BN`, это проверяет запуск.

### варианты плитки и запуск

`VARS` это список готовых размеров плитки `(MR, NR, KT)`:

```
{1,6,4}  BM 64,  BN 192, шаг k 64
{1,8,4}  BM 64,  BN 256, шаг k 64
{2,4,4}  BM 128, BN 128, шаг k 64
{1,4,4}  BM 64,  BN 128, шаг k 64
{2,6,2}  BM 128, BN 192, шаг k 32
```

все варианты помещаются в 64 кб общей памяти по формуле `(3*BM+BN)*KT*32` байт. шаг по `k` 64 на rdna4 заметно быстрее шага 32, поэтому почти все варианты берут `KT=4`. разные формы слоёв (узкие и широкие, короткие и длинные упаковки) лучше ложатся на разные плитки, поэтому вариантов несколько, а выбор делает движок замером.

`NVAR` это число вариантов.

`launch<T, TR>(v, X, Wt, C, n, m, k, ldc, acc)` запускает вариант `v`:

1. возвращает `false`, если форма не подходит: `m` не делится на `BN`, `k` не делится на шаг по `k` или `k` меньше одного шага. тогда движок считает это умножение через hipblaslt.
2. иначе считает сетку, запускает нужную копию шаблона с `P=3` и возвращает `true`.

копии шаблона перечислены в `switch` явно, потому что размеры плитки должны быть известны при сборке: от них зависят размеры массивов в регистрах и общей памяти.

запуск идёт в поток по умолчанию, синхронизации внутри нет, ошибки запуска не проверяются: это делает движок вокруг.

## 4. как движок пользуется файлом

всё это находится в `tier.cpp`, рядом с функциями `bf3gemm` и `fp3gemm`.

1. `bf3gemm` (вес bf16) и `fp3gemm` (вес fp16) раскладывают вход fp32 на три части ядрами `split3_k` и `split3_fp_k` в один буфер: старшая, средняя, младшая подряд. это ровно та раскладка `X`, которую ждёт ядро, и в ядро передаётся указатель на старшую часть.
2. `tw_on()` решает один раз за запуск движка, можно ли пользоваться своим ядром: имя архитектуры карты должно начинаться с `gfx12`, а переменная окружения `TIER_WMMA=0` выключает ядро совсем.
3. `tw_try` смотрит, есть ли уже выбранный вариант для этой формы, и если есть и он не hipblaslt, зовёт `tw::launch`. если `launch` вернул `true`, умножение готово.
4. если варианта ещё нет, умножение считается тремя вызовами hipblaslt, а после этого `tw_tune` один раз замеряет на этой форме сам hipblaslt и все варианты `VARS`. замер идёт на временном выходе, а не в настоящий `C`, потому что при накоплении повторные запуски испортили бы результат. каждый кандидат гоняется дважды. быстрейший запоминается, и если быстрее всех hipblaslt, форма помечается `-1` и дальше всегда идёт через него.
5. ключ выбора: тип веса и раскладка (`TR` или нет), `m`, корзина длины упаковки (`mbucket(n)`), `k` и есть ли накопление. упаковки близкой длины делят один выбор, так замер не повторяется на каждом шаге.
6. раскладка `TR` выбирается, когда вес передан без транспонирования и `lda` равен `m`, обычная, когда вес транспонирован и `lda` равен `k`. другие формы ядро не берёт.

## 5. что принимает и что отдаёт

принимает:

1. три части входа 16 бит подряд в видеопамяти, `[n x k]` каждая.
2. вес 16 бит в видеопамяти, `[m x k]` или `[k x m]`.
3. указатель на выход fp32 с шагом строки `ldc` и признак накопления.
4. номер варианта плитки.

отдаёт:

1. результат в `C`: запись или прибавление.
2. из `launch` признак, взялся ли вариант за эту форму.

ограничения формы: `m` кратно `BN` варианта, `k` кратно шагу по `k` и не меньше его, `n` любое. работает только на gfx12, на других картах и в сборке cuda движок до ядра не доходит.
