# tierlm.py

главный файл программы на питоне. через него идёт всё: окно, терминальные команды, обучение, разговор, сборка движка, загрузка моделей, квантованные базы. сам он ничего тяжёлого не считает, его работа это знать состояние, собрать правильное окружение и запустить нужный скрипт или движок отдельным процессом, а потом читать то, что они пишут в файлы.

# 1. что это за файл и за что он отвечает

## место в программе

`tierlm.py` это точка входа, команда `tierlm` запускает именно его (функция `main`, она в самом конце файла). файл одновременно и модуль: окно на qt (`ui.py`) делает `ui.run(sys.modules[__name__])` и дальше зовёт функции этого файла напрямую как `T.plan`, `T.train_start`, `T.chat_start`, `T.health` и так далее. то есть все правила (какой план обучения, можно ли открыть разговор, годится ли база) живут здесь, а окно только показывает и передаёт выбор.

есть второй вид интерфейса: `tierlm сервер`. тогда поднимается маленький http сервер на 127.0.0.1 и панель открывается в браузере. страница панели целиком лежит в этом же файле, в строке `PAGE` (сразу после `main` и до конца файла), сервер это класс `Handler`.

## кого он запускает

| что | как | зачем |
|---|---|---|
| `auto.sh` | `bash auto.sh [датасет]`, своя группа процессов | автопилот обучения: подбор lr, запуск `train.sh` и движка, валидация, ранняя остановка |
| `prepare.py` | `python prepare.py <файл>` | токенизация датасета в `tokens.bin`, `eval.bin`, `stats.txt` |
| `chat.py` | `python chat.py --serve [--base]` с трубами stdin и stdout | разговор с моделью, построчный json |
| `build.sh` | `bash build.sh` | сборка движка `tier` под карту |
| `fetch_model.sh` | `bash fetch_model.sh` | загрузка весов с hugging face по `HF_REPO` |
| `pydeps.sh` | `bash pydeps.sh` | установка питоновских пакетов |
| `arch.py merge` | `python arch.py merge <папка модели>` | склейка частей весов в один файл bf16 |
| движок `tier` | `tier --quantize <model.safetensors> <выход.tq> <рецепт>` | свой квант из bf16 |
| `quant.py import` | `python quant.py import <источник> <выход.tq> <model.safetensors> <движок>` | перенос готового gguf или bitsandbytes в формат `.tq` |
| `notify-send` | если окно не дало свой способ уведомлять | сообщение о конце обучения |

## какие модули он импортирует сам

1. `arch.py` (функция `amod`): `arch.tensors`, `arch.describe`, `arch.summary`, `arch.write`. по заголовкам safetensors решает что за модель и умеет ли её движок.
2. `tmpl.py` (функция `tmpl_mod`): только `tmpl.manual(семья)`, чтобы понять нужен ли jinja2 для шаблона диалога.
3. `hub.py` (функция `hmod`): каталог hugging face, проверка поддержки, сведения о модели и прогноз на этой машине.
4. `quant.py` (функция `qmod`): `quant.info(путь)` читает заголовок `.tq`.
5. `hwprobe.py`: `hwprobe.fingerprint()` отпечаток машины для сверки с движком.
6. `ui.py`: только в команде `окно`.

модули проекта грузятся лениво: перед импортом папка программы `APP` добавляется в `sys.path`. так файл можно импортировать без qt и без лишних модулей.

## главное правило про папки

программа лежит там, куда её поставил пакетный менеджер (`APP`, папка самого файла), и в свою папку ничего не пишет. всё своё живёт в `DATA`:

1. `DATA` это `TIER_DATA`, если задана, иначе `$XDG_DATA_HOME/tierlm`, иначе `~/.local/share/tierlm`. создаётся при импорте.
2. внутри: `settings.json` (настройки), `train.pid` (идущее обучение), `setup.log` (вывод сборки и загрузки), `ui.pid` (пид окна), `tier`, `tier.env`, `tier.src`, `tier.hw` (движок и его метки), `model` (папка модели по умолчанию), `work` (рабочая папка запусков по умолчанию), `models` (скачанные модели), `quant` (квантованные базы), `arch` (описания моделей для движка), `speed.json` (замеры скорости разговора).
3. все дочерние процессы запускаются с `cwd=DATA`.

# 2. как он работает

## команды терминала

| команда | что делает |
|---|---|
| `tierlm` или `tierlm окно` (`window`) | открывает окно на qt quick через `ui.py`. без pyside6 печатает что поставить и выходит |
| `tierlm учить <файл> [режим] [что]` (`train`) | обучение из терминала, в конце `exec` в `auto.sh` |
| `tierlm говорить` (`chat`) | `exec` в `chat.py` с остальными аргументами |
| `tierlm квант <рецепт или файл>` (`quantize`) | свой квант по рецепту или перенос gguf и bitsandbytes, с `nice 10` |
| `tierlm база [имя или BF16]` (`base`) | без имени список баз, с именем выбрать базу |
| `tierlm собрать` (`build`) | `exec` в `build.sh` |
| `tierlm сервер` (`server`) | панель в браузере, порт из `PORT`, по умолчанию 8800 |
| `tierlm --version`, `-v`, `версия` | печатает версию |

любая другая команда печатает формат и выходит с кодом 1.

режим в `учить` всегда `авто`: из терминала подбирается всё само, `эксперт` там не берётся. слова `быстрый`, `баланс` и `качество` тоже принимаются, означают `авто` и не считаются именем файла. что учить это `срез`, `точно`, `характер` или `lora`. если `LORA` задана в окружении, а цель не указана, цель будет `lora`. всё остальное в аргументах считается файлом датасета.

## settings.json

json словарь, читается функцией `S()`. берутся только ключи из `DEFAULTS`, остальное в файле игнорируется. пустые `MODEL` и `WORK` заменяются значениями по умолчанию, тильда раскрывается. `MODE` проходит через `mode_key`, так что в словаре всегда один из двух режимов.

| ключ | что хранит | по умолчанию |
|---|---|---|
| `MODEL` | папка текущей модели | `DATA/model` |
| `WORK` | рабочая папка запусков | `DATA/work` |
| `HF_REPO` | репозиторий текущей модели | пусто |
| `THEME` | `light` ставит светлую тему до первой отрисовки страницы | пусто |
| `MODE` | последний выбранный режим: `авто` или `эксперт`, любое другое значение при чтении становится `авто` | `авто` |
| `APPEAR` | json строка с оформлением, вставляется в страницу | пусто |
| `BG` | путь к своей картинке фона | пусто |
| `LANG` | `ru` или `en` | `ru` |
| `UI` | json строка с мелкими настройками интерфейса (`notify`, `dec` и другие), читается через `ui_pref` | пусто |
| `TAB` | вкладка `tier` или `lora` | `tier` |
| `LORA` | параметры lora строкой `16,32,qkvogud,0.05` | пусто |
| `QBASE` | имя выбранной квантованной базы (`Q4_K_M.tq`), пусто это bf16 | пусто |
| `HF_TOKEN` | ключ hugging face | пусто |
| `INFER` | настройки разговора (их пишет окно) | пусто |
| `MODELS` | json список известных папок моделей, не больше 30 | пусто |

`S_save(changes)` переписывает только переданные ключи из `DEFAULTS`, значения приводит к строке и обрезает пробелы. запись атомарная: сначала `settings.json.part` с правами 0600, потом `os.replace`. права 0600 потому что в настройках может лежать ключ hf (метка г1).

## движок и проверка его свежести

движок это файл `DATA/tier`, рядом лежат три метки, их пишет `build.sh`:

1. `tier.src` это sha1 от склеенных байт `tier.cpp`, `gpu_compat.h`, `tier_wmma.h`, `quant.h`, `quant_tables.h` именно в этом порядке (`ENGINE_SRC`).
2. `tier.hw` это отпечаток машины от `hwprobe.fingerprint()`.
3. `tier.env` это строки `КЛЮЧ=значение`, переменные без которых карта не заводится (например `HSA_OVERRIDE_GFX_VERSION` у части карт amd и у встроенных).

`engine_fresh()` (метки ж1, ж2, ж3) говорит что движок годен, если: файл есть, sha1 исходников совпадает с `tier.src` (после обновления программы старый движок требует пересборки), и отпечаток машины совпадает с `tier.hw`. отпечаток нужен потому что после замены карты или обновления rocm прежний `HSA_OVERRIDE` ведёт к зависанию карты. если `tier.hw` пустой или его нет, сверку по машине не делаем и считаем движок годным. отпечаток текущей машины считается один раз за процесс и лежит в `_HW_NOW` (метка е2). если `hwprobe` упал, отпечаток пустой и сверка тоже пропускается.

## обучение: процесс и pid файл

(раздел с метки и1)

1. `train_start(name, data, extra)` проверяет, что обучение не идёт, движок есть и свежий. потом выгружает разговор (`chat_stop`, метка н2), потому что обучению нужна вся видеопамять и озу, которые держит модель разговора.
2. окружение это `child_env(name)` плюс `extra`. `extra` это готовые числа плана: окно считает их само и отдаёт автопилоту, чтобы тот ничего не подбирал заново, показанное до запуска и есть то, что пойдёт (метка н1).
3. в `WORK/<name>_console.txt` дописывается строка `=== Запуск <дата время> ===`, туда же идут stdout и stderr.
4. `bash auto.sh [data]` запускается с `start_new_session=True`, то есть своя сессия и своя группа процессов. так обучение переживает закрытие окна, и его можно убить целиком через `killpg`.
5. в `DATA/train.pid` пишется две строки: пид и имя запуска.
6. отдельный поток делает `p.wait()`, чтобы завершившийся процесс не висел зомби (метка н3).

`train_state()` читает `train.pid` и проверяет группу через `os.killpg(pid, 0)`. возвращает `(pid, имя)` или `(None, None)`. отдельного удаления pid файла нет: мёртвая группа и есть признак, что обучение не идёт.

`train_stop()` шлёт `SIGTERM` всей группе, дописывает в консоль `=== Остановлено вручную ===` (по этой строке потом видно, что остановили руками, а не упало, метка п1), ждёт до 4 секунд с шагом 0.1 с, пока группа реально уйдёт (ответ должен быть правдой, метка п2), а через 2.5 секунды добивает `SIGKILL` (метка п3).

## продолжение запуска

`resume_env(name)` (метка о1) собирает окружение так, чтобы продолжение шло ровно с теми числами, с какими запуск начинался. источник это сообщение события `Запуск` в журнале `log.tsv`, последнее с текстом `шагов на эпоху`. из него регуляркой берутся числа:

```
LR <lr>, до <PACK> токенов в шаге, <n> шагов на эпоху × <EPOCHS> = <всего> шагов, валидация каждые <EV> шагов, снимок весов каждые <FL> шагов
```

дальше:

1. `STOP_AFTER` и `X` берутся из `env` в `run.json`.
2. `REPLAY` из `<name>_replay.txt`, если файла нет, то `0` (метка о2).
3. из `<name>_mode.txt` (строки `КЛЮЧ=значение`, его пишет автопилот) берутся `MATS`, `NSGD`, `POSDW`, `WHITEN`, `WHITEN_FRAC`, `LORA`: тот же способ, целые матрицы, nsgd, защита общих знаний (метка о3).
4. если есть `MATS`, ставится `MATS_AUTO=0`: слои уже выбраны замером при старте, продолжение учит те же (метка о4).

если в журнале нет такого сообщения, возвращается `None` и продолжать нечего.

## файлы одного запуска

все файлы запуска лежат в `WORK` с именем `<name>_<окончание>`. список окончаний в `RUN_SUFFIXES`:

| окончание | кто пишет | что там |
|---|---|---|
| `log.tsv` | автопилот и `train.sh` | журнал событий, таблица с табами |
| `console.txt` | этот файл (заголовки) и вывод `auto.sh` | весь вывод запуска |
| `stage.txt`, `stagep.txt` | автопилот | текущий этап и его ход |
| `tokens.bin`, `eval.bin` | `prepare.py` | токены обучения и отложенных примеров |
| `stats.txt` | `prepare.py` | сводка датасета строками `ключ число` |
| `source.json` | этот файл | откуда датасет: путь, размер, время, сцена |
| `prepare.txt` | вывод `prepare.py` | лог токенизации |
| `run.json` | этот файл | запись о старте: выбор, план, модель |
| `tier1.bin`, `tier1_best.bin` | `train.sh` и движок | обучаемые веса и лучший снимок |
| `step.txt`, `step_base.txt`, `elapsed.txt` | `train.sh` | шаг последнего снимка, сколько прошло |
| `mix.bin` | автопилот | данные вместе с повтором |
| `replay.txt`, `mode.txt` | автопилот | доля повтора и способ обучения |
| `lrfind.txt` | автопилот | развёртка подбора lr, строки `lrfind <шаг> <lr> <loss>` |
| `load.txt` | автопилот и `train.sh` | ход загрузки весов |
| `infer.log` | `chat.py` | лог разговора |

ещё к запуску относятся `adam_state_<name>.bin`, `tier_assignment_<name>_act.txt`, `tier_assignment_<name>_act.txt.t` и сохранённые проверки `<name>_bench_ГГГГММДД_ЧЧММСС.tsv`.

`run_files(name)` (метка бц1) ищет файлы по точным именам из этого списка, а не по началу имени: у запуска `a` не должны оказаться файлы запуска `a_b`. по этому списку считается место (`run_bytes`) и по нему же запуск удаляется (`run_delete`). место считается как `min(st_size, st_blocks * 512)`, потому что разреженный снимок весов занимает на диске меньше своего размера (метка бч1).

## формат tokens.bin и eval.bin

маленький порядок байт, всё int32:

```
n                      число примеров
повторить n раз:
  L, p                 длина примера в токенах и длина подсказки (prompt)
  L токенов            если p >= 0
  2*L чисел            если p < 0: следом идут ещё метки повтора
```

`stats()` берёт первое число каждого файла как число примеров обучения (`обучение`) и отложенных (`отложено`). `packs()` и `mix_packs()` читают только `L` и `p` и перескакивают через сами токены (метка бс2).

## stats.txt

строки `ключ число`, пишет `prepare.py`. ключи, которые использует этот файл: `examples` (без него сводки нет), `p99` (99 процентиль длины), `instr_rows` (примеров с полем instruction), `with_instr` (сколько из них пойдёт с системной репликой). ещё там есть `median`, `max`, `loss_tokens`.

## журнал log.tsv и кривые

(раздел с метки р1)

первая строка это заголовок, дальше строки с табами, первая колонка это время `ГГГГ-ММ-ДД ЧЧ:ММ:СС`. `parse_log(name)` (метка ш1) берёт столбцы по имени из заголовка, а не по счёту: журнал может обрасти новыми колонками. разбор кэшируется в `_logc` по `(mtime, size)` файла, повторный разбор только если файл изменился.

события в колонке `Событие`:

1. `Шаг`: строка шага. из неё в список `шаги` идут `Шаг`, `Эпоха`, `Loss`, `Loss_ср50`, `PPL`, `Acc_%`, `Acc_ср50_%`, `Сек_шаг`, `Ток_в_с`, `Прямой_с`, `Головка_с`, `Обратный_Adam_с`, `Токенов`, `Токенов_в_loss`, `Примеров`, `VRAM_пик_МиБ`, `VRAM_всего_МиБ`, `Живых_МиБ`, `Блоков`, `Область_МиБ`, `Мимо_области`, `ОЗУ_кэш_ГиБ`, `Обучаемая_часть_в_VRAM`, датчики карты, `|g|`, `|g|_макс`, `LR`. ещё запоминается `последний` (шаг, эпоха, lr, прошло, осталось, время).
2. `Оценка`: валидация. `Loss_отложенные`, `Лучший_отложенный`, `Acc_%`, число упаковок из текста `N упаков` в колонке `Примеров`. длительность валидации считается как разница времени со строкой шага, только если валидация идёт сразу за строкой того же шага (метки ш2, ш4), и только если она от 0 до 3600 секунд. первая валидация, до обучения, длительности не получает.
3. `Сообщение`, `Запуск`, `Завершено`, `Лучший снимок`: идут в `сообщения`. из сообщения `Запуск` регуляркой вытаскивается план: `на_эпоху`, `эпох`, `всего`, `lr`, `упаковка`, `оценка`, `сброс` (метка ш5, отсюда длина всего обучения).

если номер шага не вырос (запуск продолжили с последнего сброса или начали заново), из списков выкидываются шаги и валидации с номером от этого шага и дальше: в кривых остаётся только новая версия (метка ш3).

результат кортеж `(шаги, оценки, сообщения, последний, план)`.

`read_log(name)` собирает всё о запуске для окна и панели: разбор журнала, `stage.txt`, развёртку из `lrfind.txt`, идёт ли он сейчас, хвост консоли, состояние, `step.txt` как `продолжение`, сводку датасета, `replay.txt`, `mode.txt` как словарь `способ`, `run.json` как `выбор`, последние 40 сообщений и 60 строк вывода. `ход_этапа` и `загрузка` отдаются только у идущего запуска.

## хвост консоли и состояние запуска

`console_tail(name, n=80)` (метка ц1) читает последние 256 киб `console.txt`. куски между `ESC[?25l` и `ESC[?25h` (скрытие и показ курсора) это перерисовки терминальной панели, а не текст, их выкидываем целиком. потом снимаются коды ansi, `\r` превращается в перевод строки, пустые строки убираются, берётся только то, что после последней строки `=== Запуск `.

`run_status()` (метка ч1) даёт одно слово и, если есть, почему:

1. `идёт`, если группа процессов этого запуска жива.
2. `завершено`, если `stage.txt` равен `Завершено`. почему это последнее сообщение, начинающееся с `Остановка:`.
3. `остановлено`, если последняя строка консоли `=== Остановлено вручную`.
4. `ошибка`, если в выводе или в сообщениях есть строка под регулярку `ERR` (слова про падение, ошибки hip, hipblas, cuda, нехватку памяти, отсутствие весов и токенов, `Traceback`).
5. иначе `остановлено`, если шаги или этап были, или `нет`.

## готовность программы

(раздел с метки э1)

`health()` возвращает один большой словарь для окна и панели: версия, вид карты, компилятор (`hipcc` или `nvcc`), свежесть движка, есть ли веса и `tokenizer.json`, есть ли пакеты, идёт ли подготовка и какая, сведения о модели, карте, озу, видеопамяти, список запусков, режимы, цели, матрицы и исходные числа lora, геометрия модели, настройка оборудования, идущее обучение, диск, разговор, квантованные базы, выбранная база, размер слоёв в bf16, рецепты с размерами. отдельно в нём лежит `резерв_озу`: сколько озу движок не отдаст под кэш замороженных весов (функция `ram_reserve`, ниже).

`tokenizers` в нём считается готовым, если есть пакет `tokenizers` и либо `jinja2`, либо семья модели из `tmpl.MANUAL` с ручной разметкой: шаблон диалога у всех остальных это jinja (метка аа1).

`gpu_kind()` (метка ю1) решает, чья карта главная: у кого больше видеопамяти. встроенная radeon рядом с дискретной nvidia в ноутбуке не главная. так же решает `build.sh`. порядок: `TIER_VENDOR` если задана, потом `/sys/class/drm/card*/device/vendor` (`0x1002` amd с объёмом из `mem_info_vram_total`, `0x10de` nvidia с объёмом из `nvidia-smi`), если карт не нашлось, то по наличию `rocminfo`, `rocm-smi`, модуля amdgpu, `nvidia-smi`, `/proc/driver/nvidia`. ответ кэшируется на 60 секунд в `_gk`.

`has_module(name)` (метка я1) проверяет пакет свежим процессом `python -c "import name"`: пакет, поставленный уже после запуска программы, сам процесс не увидит, а использоваться он будет как раз из отдельного процесса. положительный ответ кэшируется навсегда, отрицательный перепроверяется не чаще раза в 3 секунды. после конца подготовки кэш `_mods` чистится.

## модель: что лежит в папке и умеет ли её движок

(раздел с метки аб1)

`model_files(mdir)` даёт список файлов весов: либо один `model.safetensors`, либо все части из `model.safetensors.index.json` (`weight_map`), если все они на месте. иначе пустой список.

`model_info()` (метка аз1) читает только заголовки safetensors, это килобайты, а не десятки гиб: имена, формы и форматы тензоров. что за модель и умеет ли её движок решает `arch.py` по тем же правилам, по которым движок её потом читает. шаги:

1. ключ кэша это `(файл, mtime, размер)` всех файлов весов плюс mtime `config.json`. при том же ключе отдаётся кэш `_minfo`.
2. `arch.tensors(папка)` даёт словарь `имя: (тип, форма)`, `arch.describe(папка)` даёт `(A, why)`: описание модели и список причин, почему движок её не возьмёт.
3. считаются параметры только текстовой части: тензоры с префиксом `prefix` из описания и голова `head`. зрение, звук и прочее, чего текстовый движок не касается, пропускаются (метка аз3).
4. отдельно считается, сколько в слоях (по `layer_prefix`) и как это делится на `mlp`, `внимание`, `прочее` (метка аз2).
5. эксперты ищутся по именам (`experts`, `block_sparse_moe`, `moe`, `shared_expert`). квант по типам из `QDT` (int8, int4, fp8, fp4, fp6, e8m0) или по окончаниям `.qweight`, `.qzeros`, `.scales`, `.weight_scale`, `.absmax`, `.quant_map`.
6. вид модели: `Dense`, `MoE`, `Quantized`, `Quantized MoE`. moe и квантованные движок не берёт: он учит только плотные модели поверх bf16.
7. если все причины отказа про `merge` (веса в нескольких файлах или не в bf16), ставится `склеить=True`: модель годится после склейки частей в один файл bf16 (`arch.py merge`).
8. в словаре: `параметров`, `эмбеддинги` (параметры минус слои), `всего_в_файле`, `типы`, `основной` тип, `слоёв`, `экспертов`, `вид`, `группы`, `семья`, `архитектура`, `модель` (подпись вида `Gemma 3 4B`, через `fam_name` и `pretty_size`), `скрытый`, `словарь`, `слой_полный`, `сводка`, `движок` (годна ли), `почему`.
9. если модель годна, описание для движка пишется функцией `arch.write` в `DATA/arch/<sha1 от ключа и версии, 16 знаков>.txt` через `.part` и `os.replace`. описание лежит рядом с данными программы, папка модели только читается (метка аз4). путь уходит в `описание`, а оттуда в `TIER_MODEL_DESC` для детей.

в `_arch` хранится два описания: `A` только если модель годна (его берёт `arch_now()`, метка аи1), и `any` в любом случае (из него `lora_geom()` берёт формы слоёв).

## каталог моделей

(раздел с метки аи2)

1. `known_dirs()` (метка ал1): папки моделей, о которых программа знает: текущая `MODEL`, список из настройки `MODELS` и все подпапки `DATA/models`. пути через `realpath`, без повторов, только существующие (текущую оставляем всегда).
2. `remember_dir(d)` дописывает папку в `MODELS`, хранится не больше 30 последних.
3. `local_models()` (метка ан1): что уже лежит на диске, список словарей `папка, модель, байт, годна, почему, текущая, repo, склеить, есть`. всё по заголовкам, без чтения весов. кэш `_local` по `(файл, mtime, размер)`. имя репозитория берётся из файла `.tier_repo` в папке модели.
4. `model_use(d)` (метка ао1): сделать папку текущей моделью. не даёт во время обучения. запоминает прежнюю и новую папку, выгружает разговор, пишет `MODEL`, чистит кэши `_minfo`, `_arch`, `_lmats`, `_bases`.
5. `hub_catalog`, `hub_check`, `hub_info` это тонкие обёртки над `hub.py` с ключом `hub_token()` (настройка `HF_TOKEN`, иначе окружение). `hub_mark` (метка аф1) дополняет строки каталога пометкой `на_диске` по `.tier_repo` локальных моделей. `hub_catalog` (метка ах1) ходит в сеть только за списком, при ошибке отдаёт кэш. `hub_check` (метка ац1) проверяет поддержку по `config.json` и заголовкам safetensors параллельно, окно зовёт её в своём потоке и получает `cb(repo, сведения)` по готовности. `hub_info` (метка ач1) даёт сведения о модели и прогноз `hub.forecast(m, hw_now())` на этой машине.
6. `hub_get(q)` (метка аэ1): скачать модель в её собственную папку `DATA/models/<орг>__<модель>` и сделать текущей. не даёт во время обучения и во время другой подготовки. пишет `.tier_repo`, сохраняет `MODEL` и `HF_REPO`, чистит кэши и запускает `setup_start('веса')`. прежняя папка остаётся в списке на диске.

`hw_now()` (метка ап1) собирает оборудование для прогноза: `ram`, `vram` (из sysfs или `vram_mib` из `tier.conf`), `disk_free` под `DATA/models`, `pcie_gen` и `pcie_width` из `шина` в `gpu_info()` (то есть из `tier.conf`, а если там 0, то замер связи карты), `tier1` (бюджет среза `tier1_params`), а также замеры прошлых запусков `anchor_step` и `anchor_tok`.

## замеры скорости

1. `speed_note(line)` (метка ар1) ловит строку разговора вида `Ответ 34 токенов: 14.91 с (0.45 с/токен)` и пишет секунды на токен в `speed.json` под именем модели. только если ответ не короче 8 токенов и только для bf16 (`chat_base` пустой): у кванта своя скорость, сравнивать не с чем. значение сглаживается: `0.7 * старое + 0.3 * новое`. вместе с ним пишется `байт = 2 * (параметров - эмбеддинги)`, это вес слоёв в bf16, чтобы прогноз мог пересчитать скорость для другой модели.
2. `tok_anchor()` отдаёт самый свежий замер разговора `(с, байт, модель)`.
3. `step_anchor()` (метка ат1) находит самый свежий по mtime журнала запуск, у которого в `run.json` есть параметры модели, и берёт медиану последних 60 значений `Сек_шаг` (нужно хотя бы 5). вместе с ней отдаёт вес слоёв bf16 того запуска, то есть сколько весов тогда ехало по шине.

формат `speed.json`:

```
{"разговор": {"<модель>": {"с": секунд_на_токен, "байт": вес_слоёв_bf16, "когда": unix_время}}}
```

## карта

(раздел с метки аю1)

1. `kfd_gfx()` (метка аю2): архитектура amd без rocm. ядро само пишет её в топологию kfd `/sys/class/kfd/kfd/topology/nodes/*/properties` как `gfx_target_version`. число переводится так: `gfx{v // 10000}{(v // 100) % 100:x}{v % 100:x}`, например 120000 даёт gfx1200, 90010 даёт gfx90a.
2. `nvidia_query(fields)` один вызов `nvidia-smi --query-gpu=memory.total,<поля>`. строки по всем картам nvidia, из них берётся та, на которой считает движок: номер из `TIER_GPU_INDEX` (зажимается в пределы списка), иначе карта с наибольшей памятью. отдаются только запрошенные поля, без `memory.total`. так имя и архитектура берутся у той же карты, что выбирает движок, а не у первой по счёту.
3. `main_pci(nv_bus)` адрес главной карты на шине pci вида `0000:01:00.0`. у nvidia его даёт `pci.bus_id` из `nvidia-smi`, он приводится к виду sysfs (домен из восьми знаков становится четырьмя). у amd это карта с наибольшим `mem_info_vram_total` в `/sys/class/drm/card*/device`. по этому адресу читаются шина и датчики, а не у `card0`, которой может оказаться встроенная.
4. `gpu_limits(slot)` пределы температур главной карты из её датчиков через `hwprobe.temp_sensors`: по полю `crit_c` и подписи датчика получаются ключи `горячая` (junction или hotspot, иначе первый датчик с пределом), `память` (mem) и `край` (edge). если датчики пределов не сообщают или `hwprobe` недоступен, ответ пустой словарь.
5. `gpu_info()`: имя архитектуры из `gpu` в `tier.conf`, иначе из kfd. для amd торговое имя берётся из `lspci -mm -d 1002:` (то, что в квадратных скобках, метка ба1), адрес карты из `main_pci()`. для nvidia имя, `compute_cap` и адрес на шине одним вызовом `nvidia_query`, архитектура `sm_XY`. шина берётся из `pcie_gen` и `pcie_width` в `tier.conf`. если там 0 (движок не смог определить связь, например карта стоит за своим внутренним мостом), поколение и ширина берутся из `hwprobe.pcie(slot)`: узкое место всей цепочки от карты до корневого порта по наибольшим договорным скоростям звеньев. в ответе `архитектура`, `название`, `производитель`, `видеопамять` (`vram_mib`), `шина` (`поколение`, `линий`), `пределы` (из `gpu_limits`). кэш `_ginfo` живёт до конца процесса.
6. `hwp()` ленивый импорт `hwprobe.py` с папкой программы в `sys.path`. если модуль не загрузился, ответ `None`, и все места, которые на него опираются (резерв озу, упаковка шага, шина, пределы температур), берут свои простые правила без осмотра машины.

## озу и видеопамять

(раздел с метки бб1)

1. `meminfo()`: `MemTotal` и `MemAvailable` из `/proc/meminfo`, в байтах.
2. `nvidia_mem()` (метка бв1): `(всего, занято)` в байтах у nvidia с наибольшей памятью. строки с `[N/A]` (встроенные, jetson) не разбираются как числа и пропускаются.
3. `vram_info()`: у amd берётся карта с наибольшим `mem_info_vram_total` и её `mem_info_vram_used`. если у nvidia памяти больше, главная nvidia (метка бг1). кто держит память: у amdgpu в `/proc/<pid>/fdinfo/*` каждого открытого файла карты есть счётчик (метка бг2). стандарт drm это `drm-total-vram` (ядра 6.x и новее), часть версий amdgpu пишет `drm-memory-vram`, единицы киб, миб или гиб (метка бг3). один клиент считается один раз по `drm-client-id`, имя процесса из `/proc/<pid>/comm`, сумма на процесс не больше всего объёма. у nvidia список берётся из `nvidia-smi --query-compute-apps`. отдаются пять самых больших.
4. `ram_reserve()` сколько озу не отдаётся под кэш весов, по тому же правилу, что в движке (`hwprobe.ram_reserve`): то, что занято сейчас (`всего` минус `доступно`), доля, которая по потолку памяти `mem_cap_pct` из `tier.conf` всегда остаётся свободной (по умолчанию 98 процентов), и 1 гиб на нужды самого процесса. если сейчас открыт разговор, его память считается свободной: перед обучением модель разговора выгружается. для этого суммируется `VmRSS` из `/proc/<pid>/status` у процесса разговора и всех его потомков (обход по `/proc/<pid>/task/*/children`), итог не больше всего объёма. без `hwprobe` резерв это четверть озу, но не меньше 5 и не больше 8 гиб.

## режимы

(раздел с метки бг4)

режимов два: `авто` подбирает всё само, `эксперт` даёт поправить каждое число плана. `MODES` список `(ключ, название, суть, значения)`, `MODE` словарь по ключу.

| ключ | lr | оценок | каждые, с | терпение | эпохи | умножение | подкачка | повтор |
|---|---|---|---|---|---|---|---|---|
| `авто` | подбор | 10 | 120 | 3 | 1.0 | `железо` | `железо` | 1.0 |
| `эксперт` | значения `авто`, плюс любые свои поля | | | | | | | |

у `авто` числа `оценок`, `каждые`, `терпение` и `эпохи` только опора: частоту валидаций и раннюю остановку `plan` считает по самим данным (число примеров, шагов в эпохе, размер отложенной выборки), а умножение и подкачку выбирает движок по оборудованию. у `эксперт` эти числа работают как есть, если поле не задано своим значением.

`mode_key(k)` приводит любой ключ к одному из двух: `авто` и `эксперт` остаются, всё остальное (в том числе `быстрый`, `баланс`, `качество` из `OLD_MODES`, пустое и неизвестное) становится `авто`. через неё проходят настройки, запрос `/api/plan`, `start_from_window` и сам `plan`. страница показывает такие ключи у прошлых запусков их полными названиями.

`GEMM` переводит выбор умножения в ключи движка: `bf3` это `--bf3`, `fp32` это `--no-bf3`, `lt` это `--no-bf3 --no-own`, `blas` это `--no-bf3 --hipblas`, `железо` ничего не добавляет и движок решает сам.

## что учить

(метки бг5, бг6, бе1)

`GOALS` словарь `ключ: (вид матриц, слои по умолчанию, подпись, описание)`:

1. `срез`: часть строк каждой матрицы и все нормировки, оптимизатор adam.
2. `точно`: целые матрицы `down_proj` трёх слоёв средней трети сети, nsgd, защита общих знаний, градиент только по ответу (`POSDW=1`).
3. `характер`: целые матрицы внимания ранней половины сети, nsgd, защита общих знаний, подмешивание.

слои по умолчанию не зашиты номерами, а считаются от глубины модели: `GOAL_FRAC` доли `1/3, 1/2, 2/3` для `точно` и `1/6, 1/3, 1/2` для `характер`. `goal_layers(goal)` даёт `round(n * доля)`, не больше `n - 1`, без повторов, по возрастанию. так на любой модели свои номера слоёв. `n_layers()` это число слоёв из геометрии модели.

## lora

(метки бж1, бж2, бз1, бк1, бл1, бн1)

классическая lora, отдельной вкладкой и без смеси с приёмами tierlm: `W + alpha/r * B·A` поверх замороженного веса, `A` равномерно в плюс минус `1/sqrt(вход)`, `B` нули, adamw fp32. матрицы пишутся буквами, как их понимает движок (`--lora r,alpha,матрицы,dropout`): `q k v o g u d` это `q_proj k_proj v_proj o_proj gate_proj up_proj down_proj` (`LORA_MATS`).

1. `LORA_DEF`: `r=16`, `alpha=32`, `tg=qkvogud`, `drop=0.05`. `LORA_LR = '2e-4'` это обычный lr для lora с adamw, он идёт только в режиме, где у самого режима задан lr. у `авто` и `эксперт` его нет, поэтому у lora по умолчанию тоже подбор, а своё число можно задать полем `LR` эксперта.
2. `lora_norm(lp)` принимает словарь или строку `16,32,qkvogud,0.05` (так она лежит в настройках и в `mode.txt`) и приводит к пределам движка: `r` от 1 до 1024, `alpha` больше 0 и не больше 65536, буквы матриц фильтруются и ставятся в порядке `LORA_MATS`, `drop` от 0 до 0.9. пустой набор матриц остаётся пустым, план потом скажет, что так нельзя.
3. `lora_arg(lp)` обратно в строку для движка.
4. `lora_geom()` раскладка слоёв: `(H, I, голов, [(голова, KV, есть_своя_v_proj)])` из описания модели. если модели нет, нули и пустой список.
5. `lora_size(lp)` сколько адаптеров и обучаемых чисел, по той же раскладке, что в движке. на каждую матрицу `r * (вход + выход)`, размеры: `q` это `H + голов*голова`, `k` и `v` это `H + KV*голова`, `o` это `голов*голова + H`, `g` и `u` это `H + I`, `d` это `I + H`. в слоях без своей `v_proj` (полное внимание у части моделей) адаптер `v` не ставится.
6. `lora_view(lp)` для карточки lora: числа, `байт = чисел * 12` (a, b и два момента adamw в fp32), `s = alpha/r`, бюджет `tier1_params * 12` из `tier.conf`.

## целые матрицы и защита общих знаний

1. `mats_params(goal, lay)` (метка бо1): сколько чисел учится в выбранных целиком матрицах. для `точно` это `H * I` на слой (down_proj). для `характер` это `2 * H * голов * голова` (q и o) плюс `H * KV * голова` за k и ещё столько же за v, если у слоя своя v_proj.
2. `whiten_bytes(goal, lay, frac)` (метка бп1): память fp32 под главные направления защиты общих знаний. на слой `int(frac * d) * d * 4` байт, где `d` это вход матрицы: `I` у down_proj, а у внимания два входа `H` (q) и `голов * голова` (o).

## шаги в эпохе

1. `packs(path, pack)` (метка бс1): сколько шагов в эпохе тем же жадным порядком, что в `train.sh` и в движке. примеры идут подряд, новая упаковка начинается, когда текущая не пустая и следующий пример в неё не влезает (`ct + L > pack`). при `pack <= 0` один пример на шаг.
2. `mix_packs(path, rp, pack)` (метка бт1): то же вместе с повтором, тем же порядком, что `replay.py mix`. к каждому примеру пристёгиваются примеры повтора, пока их токенов в loss не станет `rp` умножить на токены ответа самого примера (`L - |p|`), но хотя бы один. всё идёт в те же упаковки. длины примеров повтора оцениваются по `replay.jsonl`: примерно 3.2 знака на токен, 16 токенов разметки, в loss идёт примерно 70 процентов ответа. если файла нет, берутся средние 28 знаков вопроса и 160 знаков ответа.

## упаковка шага по видеопамяти

сколько токенов класть в шаг, решают сразу данные и карта: длинная упаковка ускоряет эпоху, но её рабочие буферы (активации) должны поместиться в видеопамять, которая остаётся вне среза.

1. `pack_room(hw)` видеопамять под рабочие буферы шага в миб: `vram_mib` минус срез (`tier1_params * 12` байт), минус запас потолка памяти (`vram_mib * (100 - mem_cap_pct) / 100`, `mem_cap_pct` зажат от 50 до 99), минус постоянная голова (словарь умножить на скрытый, bf16) и буфер подкачки одного замороженного слоя (вес слоёв bf16, делённый на число слоёв). это то, что движок оставляет вне среза. если нет `vram_mib` или `tier1_params`, ответ `None`.
2. `pack_dims(h)` размеры модели для оценки буферов: `hidden`, `inter`, `heads`, `layers`. берутся из описания модели для движка через `hwprobe.arch_dims`, иначе из `lora_geom()`.
3. `pack_auto(hw, P99, EX)` даёт пару `(токенов в шаге, пояснение)`. если есть `hwprobe` и место посчитано, упаковку выбирает `hwprobe.pack_choice(P99, EX, место, размеры)`: на маленьком наборе один пример на шаг, иначе упаковка, в которую входит хотя бы два с половиной примера длины `p99`, при этом её активации (`hwprobe.act_bytes`, та же оценка, что у движка) должны помещаться в доступную долю места. если данным подошла бы упаковка вдвое крупнее, но её буферам места не хватает, в пояснение дописывается, сколько миб требуется и сколько остаётся. без `hwprobe` или без данных о карте правило простое: до 160 токенов `p99` это 512, до 400 это 1024 на картах от 12 гб (иначе 512), длиннее одним примером на шаг.

## время шага

`step_time()` (метка бу1) берёт самый свежий запуск на этой машине и отдаёт четыре числа: среднее `Сек_шаг` (нужно хотя бы 3 шага), имя запуска, сколько токенов в шаге он укладывал (от этого длина шага зависит сильнее всего) и во сколько шагов обходится одна упаковка валидации. валидация это только прямой проход, коэффициент считается как медиана `длительность / (упаковок * сек_шага)` и зажимается в пределы от 0.15 до 1.5.

## план обучения

`plan(name, mode, over, goal, lora)` (метка бх1) самая важная функция файла. она считает точные числа будущего запуска и откуда каждое взялось, по тем же правилам, что у автопилота, только заранее: число шагов по самим токенам, а не по прикидке. окно вызывает её на каждое изменение выбора, `start_from_window` перед стартом, `учить` в терминале тоже.

вход: имя запуска (обычно черновик), режим, словарь своих полей `over` (учитывается только в режиме `эксперт`), цель (`срез`, `точно`, `характер`, `lora`) и параметры lora.

по порядку:

1. нет сводки или токенов обучения, план не считается.
2. значения режима. ключ проходит через `mode_key`, основа у обоих режимов это значения `авто`, свои поля `over` учитываются только у `эксперт`.
3. `PACK` токенов в шаге (метка бх2): до 256 примеров по одному на шаг (`0`). иначе `pack_auto` (раздел про упаковку выше): по длине примеров и по тому, помещаются ли буферы шага в видеопамять вне среза. пояснение из `pack_auto` идёт в строку плана.
4. `EPOCHS`: основа 12 эпох до 64 примеров, 6 до 512, 3 до 4096, иначе 2. умножается на `эпохи` режима и округляется, не меньше 1.
5. шагов в эпохе `packs(tokens.bin, PACK)`.
6. повтор: свой из `over`, у lora 0 (классическая lora учится только на данных, метка бх3), иначе из режима. допустимо от 0 до 4. повтор включается, только если рядом с программой есть `replay.jsonl`. если есть повтор и упаковка, шаги пересчитываются через `mix_packs`: повтор едет в тех же упаковках и часто влезает в остаток шага (метка бх4). поэтому шагов тогда пишется "около".
7. всего шагов `шагов_в_эпохе * EPOCHS`.
8. время шага из `step_time()`, если замеров нет, 3 секунды, как у автопилота (метка бх5). коэффициент валидации, если замера нет, 0.45: валидация это прямой проход по всем отложенным, упаковка стоит меньше половины шага (метка бх6). упаковок валидации `packs(eval.bin, PACK)`.
9. `EV` валидация каждые: у `авто` два раза за эпоху, `max(1, шагов_в_эпохе // 2)`, по числу шагов эпохи, а не по числу из режима. у `эксперт` `max(3, всего // оценок)`, если задано `каждые` секунд, то не реже, чем раз в столько секунд по времени шага, потолок 100 шагов при `оценок <= 10`, иначе 50. у обоих потом проверка цены: если на валидацию уходило бы больше 15 процентов времени обучения, `EV` растёт до `ceil(упаковок * k * 100 / 15)`, но не больше исходного числа (метка бх7).
10. `FL` снимок весов каждые: `EV + 1`, на шаг позже валидации, чтобы запись не совпадала с чтением.
11. `STOP_AFTER` ранняя остановка, число валидаций без улучшения. у `авто` это валидации за половину эпох: `ceil(шагов_в_эпохе / EV) * max(1, (EPOCHS + 1) // 2)`, не меньше 2. факты часто учатся рывком после плато в две или три эпохи, поэтому ранняя остановка не должна срабатывать на первом же плато. у `эксперт` `терпение` режима.
12. `LR` (метка бх8): у nsgd свой масштаб шага, готовые числа режимов подобраны для adam среза. поэтому у `точно` и `характер` всегда подбор (пусто). у среза число режима, у `авто` и `эксперт` это подбор. у lora `LORA_LR`, если у режима задан lr, иначе подбор. своё значение должно быть строго между 0 и 1. подбор это 40 коротких шагов, берётся десятая часть lr, при котором сглаженный loss минимален (это делает автопилот).
13. число валидаций `1 + ceil(всего / EV)`: первая до обучения, последняя на последнем шаге (метка бх9).
14. строка про системную инструкцию, если в данных есть поле instruction. доля и слова, при которых она идёт всегда, задаются в "данных", от них зависят сами токены (метка бх10).
15. умножение: из `over` или режима. если режим хочет `bf3`, а `tier.conf` говорит `bf16x3 0` (карта без bf16 на матричных блоках, быстрее fp32 не выйдет), то `железо` (метка бх11). в `X` добавляются ключи из `GEMM`.
16. подкачка: `вкл` это `--prefetch`, `выкл` это `--no-prefetch`, `железо` ничего.
17. свои поля эксперта: `первый` больше 1 даёт `--first-weight N`, `придержка` больше 0 даёт `--damp N`, `процессор` даёт `--cpu-share N`, `слои` вида `a:b` у среза даёт `--slice-range a:b`.
18. lora (метка бх13): параметры выбираются её карточкой, план только показывает. пустой набор матриц и адаптеры больше бюджета `tier1_params * 12` это `lim`, предел оборудования или пустой выбор, а не ошибка поля (метка бх12).
19. целые матрицы: слои правки из `over` или `goal_layers`. проверка, что это список чисел и все меньше числа слоёв. `MATS` строкой `down_proj:16,24,32` или `attn:8,16,24`. если слои не заданы руками, `MATS_AUTO=1`: автопилот перед обучением делает шесть шагов на данных и выбирает три слоя, на которые данные влияют сильнее всего (метка бх14).
20. база (метка бх15): если выбрана годная квантованная база, в `X` идёт `--qbase <путь>`, замороженное читается из кванта. негодная база это `lim`.
21. защита общих знаний для целых матриц (метка бх16): четверть главных направлений входа (`WHITEN_FRAC=0.25`), если `чисел * 6 + whiten_bytes(0.25)` влезает в бюджет, иначе десятая часть. четверть почти не уступает полному набору, десятая часть чуть слабее на большом числе правок. если не влезает и с 0.1, поле `слои правки` помечается неверным.
22. у lora диапазона слоёв нет, адаптеры во всех слоях (метка бх17).
23. оценка длительности: `всего * сек + валидаций * упаковок_валидации * k * сек`, с пометкой, если упаковка у замера была другая.

выход словарь:

| ключ | что |
|---|---|
| `ок` | можно ли запускать: нет неверных полей и пределов |
| `почему` | `неверно: поля` и тексты пределов |
| `строки` | строки плана для показа: `к` (ключ поля эксперта или пусто), `что`, `знач`, `как`, `сырое`, иногда `варианты` |
| `env` | `LR`, `EPOCHS`, `PACK`, `EV`, `FL`, `STOP_AFTER`, `X`, `REPLAY`, `MATS`, `NSGD`, `POSDW`, `WHITEN_FRAC`, `LORA`, `MATS_AUTO` для `auto.sh` |
| `шагов`, `оценок`, `длительность` | итоги |
| `запись` | сколько байт ляжет на диск: обучаемая часть с состоянием оптимизатора, умноженная на 2 (текущий и лучший снимки). у lora `чисел * 12`, у целых матриц `чисел * 6` плюс защита знаний, у среза `tier1_params * 12`. по ней страница проверяет свободное место |
| `режим`, `что`, `лора` | что в итоге выбрано |

ключи полей эксперта (`к` в строках и в `over`): `LR`, `EPOCHS`, `PACK`, `EV`, `FL`, `STOP_AFTER`, `повтор`, `умножение`, `подкачка`, `первый`, `придержка`, `процессор`, `слои`, `слои правки`, `что учить`.

## список запусков и удаление

1. `goal_of(choice, mode_txt)` восстанавливает цель запуска по `LORA` и `MATS` из `run.json` или `mode.txt`.
2. `runs_summary()` строка на каждый запуск: состояние, шаг, всего, лучший loss валидации, режим, цель, датасет, начало, прошло, есть ли веса, продолжение, когда. кэш `_rsum` по отметкам журнала, консоли, этапа, `step.txt`, `run.json`. место на диске пересчитывается не чаще раза в 30 секунд, потому что это обход каталога (метка бэ1). сортировка по времени, свежие сверху.
3. `run_delete(name)` удаляет файлы из `run_files`, не даёт удалить идущий запуск, выгружает разговор, если он с этим запуском. возвращает сколько освобождено.

## примеры из датасета

(метки бя1, бя2, ва1)

1. `read_examples(path, start, n, cap)` строки файла как есть: у `.jsonl` и `.json` каждая строка json словарь (instruction, input, output и что там ещё), у остальных строка текста идёт как `instruction`. пустые строки не считаются. каждое значение режется до `cap` знаков (4000). возвращает всего и кусок с `start`.
2. `questions(path)` первые 500 примеров как вопросы для проверки, как в обучении: `input` это реплика человека, `instruction` системная сцена, `output` ожидаемый ответ. если `input` пустой, вопросом становится `instruction`. понимает ещё `question`, `q`, `answer`.
3. `bench_save(name, head, rows)` сохраняет проверку в `WORK/<name или исходная>_bench_<дата>_<время>.tsv`. табы в значениях заменяются пробелом, переводы строк знаком `⏎`.

## разбор датасета заранее

(метки вб1, вв1, вг1)

датасет токенизируется до запуска, поэтому до старта видна точная сводка и точное число шагов. разбор идёт в один черновик `_черновик` (`DRAFT`), а при запуске его файлы (`DRAFT_FILES`: `tokens.bin`, `eval.bin`, `stats.txt`, `source.json`, `prepare.txt`) переезжают под имя запуска. так имя можно менять сколько угодно, ничего не разбирая заново и не оставляя хвостов под брошенными именами.

1. `scene_norm(sc)` сцена из instruction: `доля` от 0 до 1 (в какой доле примеров instruction идёт системной репликой) и `всегда` (слова через запятую, при которых она идёт всегда).
2. `prep_start(name, data, scene)` проверяет имя и файл, не даёт разбирать под именем уже существующего запуска (кроме черновика). новый выбор убивает недоделанный разбор (метка вг1). удаляет старые `stats.txt`, `tokens.bin`, `eval.bin`, запускает `prepare.py <data>` с `INSTR=<доля>` и `INSTR_ALWAYS=<слова>`, вывод в `prepare.txt`, пишет `source.json`. процессы разбора лежат в `prep_jobs`.
3. `prep_state(name)`: идёт ли разбор, код выхода, сводка, источник, свежий ли (размер файла тот же и mtime отличается меньше чем на секунду), последние 12 строк вывода, есть ли уже такой запуск, сцена.

формат `source.json`:

```
{"путь": "...", "размер": байт, "время": mtime, "сцена": {"доля": 1.0, "всегда": "слово1, слово2"}}
```

## подготовка: сборка, загрузка, пакеты, квант

(метки вд1, вд2, вж1, вж2)

в одно время идёт только одна подготовка, её процесс в `setup_proc`, а что именно делается в `setup_what` (окно показывает это у своей проверки). `setup_start(what)`:

| what | команда |
|---|---|
| `движок` | `bash build.sh` |
| `веса` | `bash fetch_model.sh`, только если задан `HF_REPO` |
| `склеить` | `python arch.py merge <MODEL>` |
| `пакеты` | `bash pydeps.sh` |
| `квант:<рецепт>` | `tier --quantize ...` через `quant_job` |
| `импорт:<путь>` | `python quant.py import ...` через `quant_job` |

вывод идёт в `setup.log`, файл каждый раз начинается заново с заголовка `=== <название> ===`. квант и импорт запускаются с `nice 10`: процессор и диск им в последнюю очередь, обучение и окно не тормозят.

## квантованная база

(раздел с метки вж3)

замороженные матрицы слоёв читаются из файла `.tq`, а не из bf16. обучаемое (срез, целые матрицы, lora), нормировки и эмбеддинги конвертируются из исходного bf16 в fp16 при загрузке, обучаемые веса остаются fp32. база только читается. свой квант считает движок (`tier --quantize`), готовые gguf и bitsandbytes переносит `quant.py`. базы лежат в `DATA/quant`.

1. `RECIPES`: `Q8_0`, `Q6_K`, `Q5_K_M`, `Q5_K_S`, `Q4_K_M`, `Q4_K_S`. `QB` размеры блоков `(весов в блоке, байт в блоке)`: `Q8_0` 32 и 34, `Q6_K` 256 и 210, `Q5_K` 256 и 176, `Q4_K` 256 и 144.
2. `layer_mats()` (метка ви1): матрицы слоёв исходной модели в порядке движка `[(слой, вид, строк, столбцов)]`. читает заголовок `model.safetensors` сам: 8 байт длины (uint64, маленький порядок), потом json, длина от 2 байт до 200 миб. имена по `layer_prefix` и `LAYER_MAT_TAIL`, порядок внутри слоя `MAT_ORDER`: q, k, v, o, gate, up, down. кэш по размеру и mtime файла. работает только с одним файлом `model.safetensors`.
3. `recipe_types(rec, mats)` (метка вк1): тип каждой матрицы по тем же правилам, что у движка и `llama-quantize`. у `_M` правило use_more_bits: `i < n/8 или i >= 7n/8 или (i - n/8) % 3 == 2` даёт `Q6_K` для v_proj (по счёту v_proj) и down_proj (по номеру слоя). у `Q4_K_S` первые 4 v_proj и down_proj первой восьмой слоёв идут в `Q5_K`.
4. `recipe_bytes(rec)` размер базы: каждая матрица `строк * (столбцов / блок) * байт_блока`, выровнено до 4096, плюс заголовок `матриц * 200 + 4096`, тоже до 4096.
5. `layer_bf16_bytes()` вес слоёв в bf16 для сравнения.
6. `base_list()` (метка во1): все `.tq` в `DATA/quant`, через `quant.info` (`мета`, `типы`, `матриц`) и файл сверки `<база>.tq.check` (json с `модель`, `ошибка`, `худшая`). своя база (`from` начинается с `tierlm`) годна, если `src` в мета совпадает с подписью модели `model_sig()` (размер и mtime `model.safetensors`). чужая (gguf, bitsandbytes) годна, если сверка была с этой же подписью. кэш `_bases`.
7. `qbase()` (метка вп1): выбранная база `(путь или None, запись или None, почему не годится)`.
8. `quant_job(kind, arg)` (метки вс1, вс2): команда и почему её не запустить. нужны исходная модель, свежий движок, поддержанная модель, в пути `DATA/quant` не должно быть пробела (путь базы едет в строке `X` через пробелы), на диске свободно размер базы плюс 1 гиб. для импорта: файл `.gguf`, `.safetensors` или папка bitsandbytes. кусок большой модели (`.safetensors` рядом с `model.safetensors.index.json`) берётся всей папкой. исходную модель как базу взять нельзя. имя выхода из имени источника без `-00001-of-00005`.
9. `base_pick(nm)` (метка вт1): выбрать базу для обучения и разговора, пустое имя это bf16 как в файле. берёт только годную.
10. `base_delete(nm)`: не даёт удалить во время квантования и если на базе идёт обучение (по `--qbase` в `X` из `run.json`). выгружает разговор с этой базой, удаляет `.tq` и `.check`, сбрасывает `QBASE`, если она была выбрана.

## разговор с обученной моделью

(раздел с метки ву1)

глобальное состояние:

| имя | что |
|---|---|
| `chat_proc` | процесс `chat.py --serve` |
| `chat_name` | чьи веса загружены: имя запуска, `''` только исходная модель, `None` ничего (метка ву2) |
| `chat_base` | с какой базой загружен: путь к `.tq` или `''` это bf16 (метка ву3) |
| `chat_info` | `готов`, `загрузка`, `ошибка` |
| `chat_ctx` | длина контекста загруженного разговора, 0 значит ещё не выбрана, тогда берётся `ctx_default()` |
| `chat_subs` | очереди подписчиков, каждый получает все события |
| `chat_lock` | замок вокруг смены процесса |

1. `ctx_max()` (метка вф1): сколько позиций модель видела при обучении (`max_position_embeddings` из `config.json`, с учётом `text_config`), от 256 до 32768, по умолчанию 8192. потолок потому что кэш внимания растёт с длиной.
2. `kv_per_token()` сколько байт кэша внимания на одну позицию: k и v каждого слоя в fp32, как их заводит движок. считается по строкам `layer` описания модели для движка (размер головы умножить на число kv голов), если описания нет, по `lora_geom()`. итог `2 * сумма * 4`.
3. `ctx_default()` длина контекста по умолчанию: кэш внимания берёт не больше десятой части свободной видеопамяти (`всего` минус `занято` из `vram_info`), остальное остаётся под постоянные матрицы, от которых зависит скорость ответа. шаг 256, от 256 до `ctx_max()`. если замера нет, 1024, но не больше `ctx_max()`.
4. `gen_defaults()` (метка вх1): выборка, которую задумали авторы модели (`generation_config.json`), как есть, без догадок. `do_sample: false` даёт температуру 0, остальное `temperature`, `top_k`, `top_p`, `min_p`, `repetition_penalty` (как `повтор`).
5. `chat_start(name, ctx, base)` (метки вя1, вя2, вя3): `name` это запуск с сохранёнными весами или `''` для исходной модели. тот же процесс отвечает и исходной моделью (переключение без перезагрузки весов), поэтому другой запуск грузится, только когда он правда другой. `ctx` это длина контекста, под неё движок заводит кэш внимания, поэтому другая длина это перезагрузка. без `ctx` берётся длина уже загруженного разговора, а если его ещё не было, `ctx_default()`. `base=None` берёт выбранную базу (у кванта больше весов в видеопамяти, ответ быстрее), `base=''` всегда bf16, иначе имя годной базы. процесс `chat.py --serve [--base]` с окружением `child_env(name или 'run')`, плюс `QBASE` и `CTX`, своя группа процессов, stdin и stdout построчно.
6. `chat_reader(p)` читает stdout построчно, каждая строка json. `ready` ставит `готов`, `load` это ход загрузки, `ошибка` запоминается, `end` с `скорость` идёт в `speed_note`. каждое событие кладётся во все очереди `chat_subs`. события от старого процесса, который уже сменили, отбрасываются. если процесс закрылся сам, а не сменён другим, подписчики получают `{"end": true, "закрыт": true, "ошибка": ...}` (метка га1).
7. `_chat_kill()` (метка вч1): `SIGKILL` всей группе. `chat.py` и движок под ним одна группа процессов, гаснут вместе. веса только читались, им ничего не грозит.
8. `chat_stop()` (метка вш1): выгрузить модель разговора, озу и видеопамять освобождаются сразу. кто ждал ответа, получает `{"end": true, "закрыт": true, "остановлено": true}`.
9. `run_model_why(name)` (метка вэ1): запуск учился на другой модели (другое число параметров или другая папка), его веса к нынешней не подходят, формы и смысл другие.
10. `chat_blocked(name)` (метка вю1): почему модель разговора сейчас не загрузить. обучение и разговор оба занимают всю свободную видеопамять карты (срез обучения считается от её объёма, разговор держит в ней столько весов, сколько влезет). второй процесс отнял бы память у первого посреди шага, поэтому, пока идёт обучение, новый разговор не открывается. уже открытый разговор не мешает: `train_start` сам выгружает его перед стартом.

запрос в разговор это одна json строка в stdin `chat.py`. сервер пересылает из тела только ключи `q`, `new`, `base`, `temp`, `max`, `сцена`, `сила`, `top_k`, `top_p`, `min_p`, `повтор`, `зерно`.

## настройка оборудования tier.conf

(метки гб1, гг1, гг2)

файл `~/.config/tier.conf` (или `TIER_CONF`) пишет сам движок при осмотре машины. формат строки `ключ значение` через первый пробел. ключи, которые читает этот файл: `gpu`, `vram_mib`, `pcie_gen`, `pcie_width`, `tier1_params` (бюджет обучаемых чисел в видеопамяти, на число 12 байт: вес и два момента adam), `bf16x3`, `prefetch`, `headroom_mib`, `mem_cap_pct`.

`conf_write(changes)` переписывает только названные ключи, остальное в файле это осмотр оборудования, его трогать нельзя. новые ключи дописываются в конец. `mem_cap_pct` потолок памяти в процентах, целое от 50 до 99, иначе значение не записывается. если файла нет, ничего не пишется и ответ `False`. через панель можно менять только `headroom_mib`, `tier1_params`, `bf16x3`, `prefetch`, `mem_cap_pct`.

## http сервер

класс `Handler`, `ThreadingTCPServer` на `127.0.0.1`, каждый запрос в своём потоке, протокол http 1.1, ответы с `Cache-Control: no-store`. `serve(port)` (метка гк1) поднимает сервер (порт 0 это свободный порт), запускает `watch_runs` и возвращает `(srv, адрес)`.

запросы get:

| путь | ответ |
|---|---|
| `/`, `/index.html` | страница `PAGE` с подстановками |
| `/bg` | своя картинка фона из `BG`, только чтение и только png, jpg, webp, avif, gif (метка гд6) |
| `/logo.svg` | `APP/logo.svg` |
| `/font/<имя>.woff2` | шрифт из `APP/fonts` |
| `/api/state?run=` | `read_log(run)` |
| `/api/stream?run=` | поток sse с `read_log(run)` |
| `/api/health` | `health()` |
| `/api/setup/stream` | поток sse вывода `setup.log` |
| `/api/chat/stream` | поток sse событий разговора |
| `/api/settings` | `свои` (настройки), `железо` (`tier.conf`), `пути` |

если `run` не задан, берётся идущий запуск, иначе последний по имени, иначе `run`.

запросы post, тело json:

| путь | что делает |
|---|---|
| `/api/start` | `start_from_window(body)` |
| `/api/plan` | `plan` по черновику, `prep_state` черновика, проверка имени, `lora_view` |
| `/api/prepare` | `prep_start(DRAFT, датасет, сцена)` |
| `/api/stop` | `train_stop()` |
| `/api/kill` | остановить обучение, разговор, подготовку и разборы, ответить и через 0.3 с `os._exit(0)` (метка гд7) |
| `/api/setup` | `setup_start(что)` |
| `/api/base` | `base_pick` или `base_delete` (если `удалить`) |
| `/api/settings` | `S_save(свои)`, `conf_write` разрешённых ключей `железо` |
| `/api/chat` | проверки и запрос в разговор |
| `/api/chat/stop` | `chat_stop()` |
| `/api/runs/delete` | `run_delete(имя)` |
| `/api/peek` | `read_examples(путь, с, n)`, `n` от 1 до 50 |
| `/api/questions` | `questions(путь)` |
| `/api/bench/save` | `bench_save` |

в `/api/chat` запуск без `step.txt` не открывается: срез без единого сброса весов это нули вместо весов, модель несёт мусор (метка гд8).

потоки:

1. `stream_state` (метки гд1, гд2): раз в 0.3 с сравнивает отметки журнала, `train_state`, `stage.txt`, `lrfind.txt`, `load.txt`, `stagep.txt`. сервер сам толкает обновление, как только журнал вырос, обучение началось или кончилось, или сменился ход загрузки и этапа. без изменений толкает раз в 10 секунд.
2. `stream_setup` (метка гд3): вывод сборки или загрузки по мере появления, в конце `конец`, `код` и свежая `готовность`.
3. `stream_chat`: каждый подписчик получает свою очередь в `chat_subs`, раз в 10 секунд пустой комментарий `: ждём`, чтобы соединение не засыпало.

подстановки в странице (метки гд4, гд5): при `THEME=light` в `<html>` ставится `data-theme="light"` до первой отрисовки, иначе светлая тема мигнула бы тёмной при каждом запуске. `/*APPEAR*/{}` и `/*UI*/{}` заменяются json из настроек, `/*LANG*/'ru'` языком. в json `</` экранируется, чтобы текст не закрыл тег `script`.

## старт из окна

`start_from_window(body)`:

1. `продолжить`: `resume_env`, проверка что модель та же (`run_model_why`), что база из `X` ещё существует, и `train_start(name, '', env)`.
2. новый запуск: имя годно и свободно (`name_state`), обучение не идёт, черновик разобран и свежий, план черновика `ок`.
3. файлы черновика переезжают под имя запуска (метка гж1), план считается ещё раз уже по имени запуска, `train_start` с `env` плана.
4. при успехе пишется `<name>_run.json` (метка м1 у `run_choice`): `режим`, `режим_имя`, `свои`, `что`, `лора`, `база`, `env`, `строки`, `шагов`, `начало`, `датасет`, `модель` (`модель`, `вид`, `основной`, `параметров`, `эмбеддинги`, `папка`, `семья`). этот файл потом читают продолжение, список запусков, замеры скорости и проверка модели разговора.

## уведомления

(метки а2, гз1)

`watch_runs()` раз в 2 секунды смотрит имя идущего запуска. когда оно сменилось, а прежний был, и уведомления включены (`notify` в `UI`), шлёт сообщение: завершено с лучшим loss или ошибка с причиной. остановленные руками не сообщаются. пока окно открыто, конец обучения видит этот поток, а показывает уведомление само окно: `ui.py` кладёт в `NOTIFY` свою функцию через трей qt. если её нет или она упала, `notify-send`. когда окно закрыто, о конце сообщает автопилот `auto.sh` сам, по `TIER_NOTIFY`.

## окно

команда `окно` (метка гл5): импорт `ui`, при ошибке текст, что поставить (pyside6 с qt quick), и подсказка про `tierlm сервер`. в `DATA/ui.pid` пишется пид, при выходе файл удаляется, только если там всё ещё наш пид. `ui.run(модуль)` возвращает ложь, если qt не загрузил `ui.qml`.

## терминальное обучение

команда `учить` (метка гл1):

1. имя запуска из `NAME`, по умолчанию `run`.
2. если журнал запуска уже есть: с файлом ошибка (для новых данных нужно другое имя), без файла продолжение через `resume_env`.
3. иначе `prepare.py` сразу под имя запуска (без черновика), потом `plan(name, 'авто', goal, lora=LORA)`, печать строк плана.
4. переменные `LR`, `EPOCHS`, `PACK`, `EV`, `FL`, `STOP_AFTER`, `X`, `REPLAY`, `MATS`, `NSGD`, `POSDW`, `WHITEN`, `WHITEN_FRAC` из окружения заменяют числа плана.
5. `os.execvpe` в `bash auto.sh`: процесс `tierlm` превращается в автопилот, своей группы и `train.pid` тут нет.

`говорить` (метка гл2) берёт ту же базу, что выбрана в окне, если `QBASE` не задана. `квант` (метка гл3) это то же задание, что кнопками в окне, свой квант или перенос. `база` (метка гл4) без имени печатает список со звёздочкой у выбранной, с именем выбирает, `BF16` это исходные веса.

## страница панели `PAGE`

строка `PAGE` это вся панель для режима `сервер`: html, css и js в одном куске, без внешних библиотек. окно на qt её не использует, у него свой `ui.qml`. в странице:

1. язык: страница пишется по русски, а английский накладывается словарём кусков при появлении текста (длинные куски первыми).
2. оформление сводится к переменным css и ставится до первой отрисовки.
3. виды: `v-setup` (новое обучение: модель, режим, что учить, lora, данные, справа план), `v-train` (ход обучения и кривые), `v-runs` (запуски, сравнение, удаление), `v-chat` (разговор), `v-bench` (проверка вопросами, обученная против исходной), `v-settings` (оформление, графики, поведение, разговор, оборудование, пути, клавиши, о программе).
4. кривые рисуются на canvas в настоящих пикселях, из каждой горсти точек берутся низ и верх, чтобы всплески не пропадали.
5. палитра команд и клавиши.
6. пределы температур на вкладке температуры берутся из `гпу.пределы` в `health`: троттлинг ожидается на 10 градусов ниже предела датчика (`tWarn`), предел кристалла показывается из датчика. если датчик предела не сообщает, порог 95 градусов и предел около 110.
7. проверка озу перед обучением берёт `резерв_озу` из `health`, то же правило, что в движке, проверка диска сравнивает свободное место с `запись` плана с запасом 10 процентов (без плана порог 20 гиб).
8. все данные страница берёт через `/api/*` выше, состояние запуска через `EventSource` на `/api/stream`.

короткие js комментарии внутри `PAGE` оставлены в коде, по ним удобно искать нужный кусок страницы.

# 4. что важно знать, когда его правишь

1. файл это и программа, и модуль для `ui.py`. имена функций и глобальных переменных, которые зовёт окно (`plan`, `health`, `train_start`, `train_stop`, `train_state`, `start_from_window`, `chat_start`, `chat_stop`, `chat_blocked`, `chat_proc`, `chat_subs`, `setup_proc`, `prep_jobs`, `DRAFT`, `LORA_DEF`, `LORA_MATS`, `LORA_LR`, `NOTIFY`, `watch_runs` и другие), это внешний интерфейс. переименование ломает окно.
2. ключи словарей русские (`ок`, `почему`, `шаги`, `оценки`, `строки`, `знач`, `как`), их читают и `ui.py`, и `PAGE`. менять ключ нужно во всех трёх местах.
3. в программу ничего не пишется: всё только в `DATA`, `WORK`, `MODEL/.tier_repo` и `tier.conf`. папка модели кроме `.tier_repo` только читается.
4. `plan` должен считать так же, как автопилот, `train.sh` и движок: жадная упаковка в `packs`, порядок повтора в `mix_packs` как `replay.py mix`, правила `PACK`, `EV`, `FL`. если поменять правило там, нужно поменять и здесь, иначе показанное число шагов не совпадёт с тем, что пойдёт.
5. продолжение держится на тексте сообщения `Запуск` в журнале (регулярка в `resume_env` и в `parse_log`). если автопилот поменяет формулировку, продолжение и план в кривых перестанут находиться.
6. журнал разбирается по именам колонок. новые колонки добавлять можно, переименовывать существующие нельзя без правки `parse_log` и `step_anchor` (там `Сек_шаг` ищется по заголовку отдельно).
7. `run_files` берёт только точные имена. новый файл запуска нужно добавить в `RUN_SUFFIXES`, иначе он не будет считаться в месте и не удалится вместе с запуском. черновые файлы, которые переезжают при старте, перечислены в `DRAFT_FILES`.
8. `train.pid` не удаляется, признак жизни это `os.killpg(pid, 0)`. обучение всегда должно стартовать со `start_new_session=True`, иначе `killpg` убьёт не то или окно потянет обучение за собой.
9. обучение и разговор не живут вместе: `train_start` выгружает разговор, `chat_blocked` не даёт открыть разговор во время обучения. оба процесса берут всю свободную видеопамять.
10. `chat_proc`, `chat_name`, `chat_base`, `chat_ctx` меняются только под `chat_lock`. `chat_reader` отбрасывает строки от процесса, который уже не `chat_proc`. каждый запрос в разговор должен получить ровно один ответ `end`, на этом стоит очередь разговора и проверки в странице.
11. сервер многопоточный. кэши (`_logc`, `_rsum`, `_minfo`, `_arch`, `_local`, `_lmats`, `_bases`, `_mods`, `_gk`) это простые словари без замков, расчёт на то, что повторный расчёт безопасен и даёт то же. при смене модели нужно чистить `_minfo`, `_arch`, `_lmats`, `_bases`, как это делают `model_use` и `hub_get`. `_ginfo` (карта) не чистится до конца процесса.
12. сервер слушает только `127.0.0.1` и не проверяет, кто спрашивает. `/api/peek` и `/api/questions` читают любой путь из тела запроса. открывать его наружу нельзя.
13. в пути `DATA/quant` не должно быть пробелов: `--qbase <путь>` едет внутри строки `X`, которую автопилот режет по пробелам, и `qbase_of_x` ищет путь как `\S+`.
14. своя база годна, пока подпись модели (размер и mtime `model.safetensors`) та же, что при квантовании. `layer_mats` и `model_sig` смотрят только на один файл `model.safetensors`, модель из частей сначала склеивается.
15. бюджет видеопамяти под обучаемое это `tier1_params * 12` байт. у lora на число 12 байт (вес и два момента), у целых матриц в плане `6` байт на число плюс защита знаний в fp32. эти множители должны совпадать с тем, что реально выделяет движок. то же про `pack_room`, `ram_reserve` и `kv_per_token`: они повторяют расчёт движка, и если он поменяется там, оценки здесь нужно поправить вместе с ним.
16. `has_module` и подобные проверки идут отдельным процессом специально: пакеты ставятся из `pydeps.sh` во время работы программы.
17. `settings.json` пишется с правами 0600 и через временный файл. ключ, которого нет в `DEFAULTS`, не сохранится и не прочитается, новую настройку нужно сначала добавить туда.
18. `conf_write` не создаёт `tier.conf`, его создаёт движок при осмотре. строки, которые не названы в изменениях, сохраняются как есть.
19. все тексты для человека в этом файле по русски. английский язык делает окно и страница своим словарём поверх текста, поэтому менять формулировку сообщения значит, что её перевод может перестать находиться.
20. `hwprobe` здесь необязателен: у каждой опоры на него (`hwp()`) есть запасное правило. новое место, которое берёт данные из `hwprobe`, тоже должно работать, когда `hwp()` вернул `None`.
