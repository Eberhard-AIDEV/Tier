# tmpl.py

## 1. что это за файл и за что он отвечает

tmpl.py превращает диалог в токены так, как этого ждёт сама модель. для этого берётся шаблон диалога из репозитория модели (`chat_template` из `chat_template.jinja`, `chat_template.json` или `tokenizer_config.json`) и рендерится через jinja2. исключение это семьи из `MANUAL` (сейчас только gemma 4): их разметка сделана вручную, тем же порядком токенов, на котором проверен движок. все остальные модели, включая gemma 2 и 3, идут через свой шаблон. если шаблон не знает роли system, инструкция ставится в начало первого сообщения пользователя.

файл нужен в двух местах: в разговоре (собрать подсказку перед ответом модели) и при подготовке обучающего набора (разделить пример на часть вопроса и часть ответа, чтобы учить только ответ).

кто его вызывает:

1. `chat.py`: `F = Fmt(M, tok)`, потом `F.prompt(scene, история)` перед каждым ответом, `F.stop` чтобы понять, где ответ кончился, и `F.think` для переключения размышлений.
2. `prepare.py`: `F = Fmt(M, tok)` и `F.example(инструкция, вопрос, ответ)` для каждого примера набора.
3. `hub.py`: `tmpl.manual(family)`, чтобы не считать модель без шаблона базовой, если для её семьи есть ручная разметка.
4. `tierlm.py`: `tmpl_mod().manual(семья)`, чтобы решить, нужен ли модуль jinja2 для этой модели.

что вызывает сам: других файлов проекта не импортирует. снаружи нужен токенизатор (объект `tokenizers.Tokenizer`, его создаёт вызывающий) и jinja2 (импортируется лениво, только при первом рендере, поэтому для gemma 4 jinja2 не нужен).

## 2. как он работает

командной строки и переменных окружения у файла нет, это модуль.

### что читается из папки модели

| файл | что берётся |
|---|---|
| `config.json` | `model_type` (с наложенным `text_config`), `eos_token_id` если нет в `generation_config.json` |
| `tokenizer_config.json` | `chat_template`, `bos_token`, `eos_token` |
| `special_tokens_map.json` | `bos_token`, `eos_token`, если их нет в `tokenizer_config.json` |
| `chat_template.jinja` | текст шаблона, у него первый приоритет |
| `chat_template.json` | поле `chat_template`, второй приоритет |
| `generation_config.json` | `eos_token_id` (число или список) |

любой файл, который не читается или не разбирается, считается пустым словарём.

шаблон бывает списком именованных шаблонов, тогда берётся тот, у которого `name` равно `default`, иначе первый. значения `bos_token` и `eos_token` бывают строкой или словарём с полем `content`, оба вида понимаются.

### поток

1. в `__init__` определяется, gemma 4 это или нет (метка в1): по семье из config.json, а если её нет, то по словарю токенизатора (есть оба токена `<|turn>` и `<|channel>`).
2. собирается множество `stop`: все `eos_token_id` из `generation_config.json` (или из `config.json`). у gemma 4 к ним добавляются `<turn|>` и id 1. у остальных добавляется id текстового `eos_token`, если он есть в словаре.
3. `think = False` (метка в2): размышления по умолчанию выключены, модель сразу отвечает. передаётся в шаблон как `enable_thinking`.
4. если это не gemma 4 и шаблона нет, конструктор выходит через `SystemExit` с объяснением: модель базовая и не предназначена для разговора.
5. дальше вызывающий зовёт `prompt()` или `example()`.

### что на выходе

списки id токенов (целые числа). кодирование всегда через `tok.encode(s, add_special_tokens=False)`, токенизатор сам ничего не добавляет. всё, что нужно (bos, маркеры ролей), должно прийти из шаблона текстом или, у gemma 4, явными id. в текст шаблона bos попадает через переменную `bos_token`, и токенизатор узнаёт его как специальный токен по тексту.

## 3. главные функции и разделы

### `MANUAL`, `manual(model_type)`

`MANUAL` это кортеж начал `model_type`, для которых есть проверенная ручная разметка, им шаблон из репозитория не обязателен (метка а2). `manual()` отвечает, начинается ли `model_type` (в нижнем регистре) с одного из них. от этого зависит, можно ли обойтись без `chat_template` и без jinja2 (метка б1).

### `Fmt.__init__(mdir, tok)`

описан в потоке выше. поля объекта: `tok`, `mdir`, `enc` (кодирование без спецтокенов), `gemma4`, `src` (текст шаблона или `None`), `bos`, `eos` (текст), `stop` (множество id), `think`, `_t` (скомпилированный шаблон, создаётся при первом рендере), `nosys` (шаблон не понимает роль system).

### `_render(msgs, gen)`

рендер шаблона jinja2.

1. при первом вызове создаётся `ImmutableSandboxedEnvironment` с `trim_blocks` и `lstrip_blocks` (так рендерит transformers), с расширением `jinja2.ext.loopcontrols` (`break` и `continue` в циклах) и своим расширением `Generation`. в глобальные имена кладутся `raise_exception` (бросает `ValueError`) и `strftime_now` (текущая дата по формату, её зовут некоторые шаблоны).
2. расширение `Generation` (метка в3): теги `{% generation %}` и `{% endgeneration %}` это разметка ответа модели из transformers (шаблоны smollm3 и других). transformers по ней строит маску ответа, нам маска не нужна, поэтому содержимое просто выводится как есть.
3. в шаблон передаются `messages` (список словарей `role`, `content`), `add_generation_prompt`, `bos_token`, `eos_token`, `enable_thinking`.
4. если шаблон бросил `ValueError`, а первое сообщение это system, значит шаблон не знает роли system (gemma 1 и 2). тогда ставится `nosys = True`, и инструкция переносится в начало первого сообщения пользователя, как советует сама модель (метка в4). дальше все рендеры этого объекта сразу идут со сложенным system.

### `_fold(msgs)`

складывает system в первое сообщение пользователя: `system + "\n\n" + текст пользователя`. если первым после system идёт не пользователь, вставляется новое сообщение пользователя с текстом system. исходный список не меняется, сообщения копируются.

### ручная разметка gemma 4 (метка в5)

1. `_g4turn(role, text)`: `<|turn>`, потом текст `role + "\n" + text`, потом `<turn|>`, потом `"\n"`.
2. `_g4model()`: начало ответа модели: `<|turn>`, текст `"model\n"`, `<|channel>`, текст `"thought\n"`, `<channel|>`. то есть канал размышлений сразу закрыт пустым, и модель начинает с ответа.

спецтокены здесь берутся по id через `tok.token_to_id`, а не текстом, чтобы порядок токенов был ровно тот, на котором проверен движок. флаг `think` на ручную разметку gemma 4 не влияет.

### `prompt(system, turns)` (метка в6)

`system` это сцена или пустая строка, `turns` это список пар `[(вопрос, ответ), ..., (вопрос, None)]`. результат: токены до начала ответа модели.

1. gemma 4: `<bos>`, ход system (если сцена не пустая), для каждой пары ход пользователя, и если ответ есть, `_g4model()`, ответ, `<turn|>`, `"\n"`. в конце `_g4model()`.
2. остальные: собирается список сообщений `system`, `user`, `assistant` и рендерится с `add_generation_prompt=True`.

`chat.py` обрезает историю спереди, пока подсказка плюс длина ответа не влезет в контекст, и каждый раз заново зовёт `prompt()`.

### `example(system, user, answer)` (метка в7)

пример обучения превращается в пару `(токены вопроса до начала ответа, токены ответа с концом реплики)`.

1. gemma 4: вопрос это `prompt(system, [(user, None)])`, ответ это токены ответа и `<turn|>`.
2. остальные: `p` это рендер без ответа с `add_generation_prompt=True`, `f` это рендер с ответом и `add_generation_prompt=False`. если `f` начинается с `p` и в остатке есть текст ответа, ответом считается остаток `f[len(p):]` без хвостовых переводов строки. так в ответ попадают и маркеры конца реплики, которые ставит шаблон.
3. если шаблон переписывает прошлое (например вырезает размышления из прошлых ответов), `f` уже не продолжает `p`. тогда ответ берётся как есть, и в конец ставится id `eos_token`, если он есть в словаре (метка в8).

## 4. что важно знать, когда правишь

1. ручная разметка gemma 4 должна давать токены один в один с тем, на чём проверен движок. любое изменение в `_g4turn`, `_g4model`, `prompt` или `example` для gemma 4 меняет и разговор, и обучение.
2. `prompt()` и `example()` для одной модели должны давать согласованную разметку: вопрос из `example()` должен совпадать с тем, что `prompt()` даёт для одного хода. иначе модель учится на одном виде, а в разговоре видит другой.
3. вопрос и ответ в `example()` кодируются отдельно. на границе это может дать другие токены, чем кодирование всей строки разом. это принятое допущение.
4. кодирование всегда без спецтокенов. если включить `add_special_tokens`, bos задвоится.
5. окружение jinja2 песочница (`ImmutableSandboxedEnvironment`), потому что шаблон это чужой код из репозитория. не меняй его на обычное окружение.
6. признак `nosys` выставляется один раз на объект и дальше не сбрасывается. если шаблон бросил `ValueError` по другой причине, а первое сообщение было system, его тоже примут за "не знает system", и второй рендер покажет настоящую ошибку.
7. `stop` должен содержать все id, которыми модель заканчивает реплику, иначе `chat.py` не остановит генерацию вовремя. у gemma 4 это `<turn|>` и 1.
8. `enable_thinking` передаётся всем шаблонам. шаблоны, которые его не знают, просто его не используют. `chat.py` при смене `think` очищает историю, потому что разметка прошлых ходов меняется.
9. если добавляешь семью в `MANUAL`, `hub.py` и `tierlm.py` перестанут требовать для неё шаблон и jinja2, поэтому ручная разметка для неё должна быть написана целиком в `prompt()` и `example()`.
